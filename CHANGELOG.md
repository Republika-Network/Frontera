### Documentation

- **Authority-control platform architecture (documentation only — no source, schema, API or behaviour change).** Records the current-state measurement, the gap analysis, and the proposed target architecture for evolving Frontera from its present shape into an explicitly layered authority-control platform, under the thesis that Frontera governs *under what authority* an action may be exercised across a system boundary and never replaces a target system's IAM, RBAC, authentication or signing.
  - `docs/architecture/CURRENT_STATE_AUTHORITY_CONTROL.md` — measured current state (topology, decision path, domain inventory, the frozen HTTP surface, persistence, tests, frontend), the mapping of today's code onto the target `request → authority → context → policy → obligations → bounded grant → action → revocation/expiry → evidence` lifecycle, and ten recorded gaps. Also records two corrections to the framing this work was requested under: there is no XRPL code, dependency or document anywhere in this repository (the ledger-adjacent adapter is Pinata/IPFS behind the generic provider-adapter contract), and the Sovereign Access lifecycle is already provider-neutral, so there is no chain coupling to generalize away from.
  - `docs/architecture/TARGET_AUTHORITY_CONTROL_ARCHITECTURE.md` — the proposed seven-layer target (Authority, Policy, Context, Obligations, Grants, Evidence, Intelligence), the one-directional dependency rule and its six invariants, the design of the two genuinely new mechanisms (context provenance/trust, and policy derived values), an additive package/module structure, a migration strategy that preserves existing Sovereign Access behaviour exactly, a thirteen-phase implementation sequence, and eleven recorded architectural risks.
  - `docs/architecture/ADR-AUTHORITY-CONTROL-LAYERING.md` — adopts the seven layers as a naming and boundary decision rather than a refactor; layers are contracts enforced by types and structural tests, never directories or deployment units.
  - `docs/architecture/ADR-CONTEXT-PROVENANCE-AND-TRUST.md` — the requesting actor may state what it wants to do, never a fact that decides whether it may. Generalizes the existing two-key `organizationId`/`organizationName` self-assertion defence in `src/kernel/orchestration/request-adapter.ts` into a typed context layer with sources, facts, four trust classes (`attested`/`authoritative`/`derived`/`asserted`), freshness, and `resolved`/`unresolved`/`stale`/`conflicted` as first-class resolutions.
  - `docs/architecture/ADR-OBLIGATION-DISCHARGE-AND-BOUNDED-GRANT.md` — closes the two missing lifecycle edges: obligations gain a six-state discharge lifecycle (and nothing more — no routing, scheduling or notification), and a grant becomes derivable from a *verified* decision under attenuation-only bounds, checked inside the issuing store transaction.
  - `docs/architecture/ADR-DETERMINISTIC-AUTHORIZATION-AI-BOUNDARY.md` — AI may interpret, recommend, explain, detect signals and propose policy; AI may never be the final authorization authority. Replaces a prohibition currently distributed across a dozen module READMEs with a structural boundary (non-decisional advisory types, an import-boundary lint, and determinism tests), and states the settling test: removing every advisory producer must change no decision anywhere.

### Added
- **Obligation Runtime (layer D) — a deterministic discharge lifecycle for obligations, with no change to any authorization decision.** Implements `docs/architecture/ADR-OBLIGATION-DISCHARGE-AND-BOUNDED-GRANT.md`'s first half: `require-approval` stops being, in the ADR's words, "a statement the platform makes and never keeps". A declared obligation gains a closed lifecycle, a discharge gains provenance, and an action the Kernel authorized *conditionally* does not execute until the condition is met. See `src/features/obligation-runtime/README.md`.
  - **The invariant, and the whole point.** An obligation never changes the meaning of an authorization decision. An allowed action whose blocking obligation is undischarged reports `status: 'allowed'` alongside `obligations.exerciseEligibility: 'blocked'`, and the executor does not run — it is never rewritten into a denial. ADR §3: collapsing the two "would erase the distinction between 'policy said no' and 'policy said yes, conditionally, and the condition was not met'". Settled by deletion rather than by inspection: one request is evaluated with no capability and at four lifecycle states, and the authorization half of the result is byte-identical every time.
  - **The lifecycle.** All seven nodes the ADR diagram draws — `required`, `pending`, `discharged`, `verified`, `rejected`, `waived`, `expired` — with the eight legal transitions between them and nothing else. Illegal transitions are reported, never repaired: a terminal obligation is not reopened, a refusal does not invent a discharge to refute, and an out-of-order observation does not rewrite history. `required` is the declared state Layer B hands over; the six states Layer D manages are the rest, which reconciles the ADR's "six states" prose with its seven-node diagram without collapsing any of them. One documented divergence: `pending → expired` is not drawn in the ADR and is implemented because ADR §6 makes expiry clock-derived; it can only ever withhold exercise.
  - **`verified` is not `discharged`.** A discharge reported by a source the deployment classifies as self-reporting reaches `discharged` and stops there; only an *independent* source — an approval runtime, a provider adapter, a verified attestation — reaches `verified`, and only `verified` and `waived` satisfy a blocking obligation. The class comes from operator configuration and from nowhere else: `ObligationDischargeObservation` has no `verificationClass` field, no `state` field, and no way to acquire either through the port.
  - **Kernel integration.** `ObligationDischargeProvider` is a fifth optional port alongside `policyPackProvider`, `governedAuthorityProvider`, `governedConstraintProvider` and `contextResolution`. `evaluate()` reports the lifecycle, the blocking aggregate and the exercise eligibility; `enforce()` withholds the executor and reports `execution.withheldBy: 'obligation'` over an untouched decision. Obligation state never reaches the policy input — the dependency runs `D reads B`, never back — so no policy rule can turn on whether an obligation was discharged.
  - **Security boundary.** A caller cannot discharge its own obligation. Obligation state has exactly one producer, the configured provider, and `ObligationDischargeQuery` carries no requester bag, so nothing a caller sends is ever consulted; the `aoc.obligations` namespace is stripped from the free-form context bag regardless. An adversarial suite submits the forgeries a caller would actually try — `financeApproved: true`, `obligation.state: 'DISCHARGED'`, a fabricated `aoc.obligations` — plus discharges citing an unregistered source, the wrong obligation, the wrong request, the wrong action and a stale window, and none of them opens the gate. A deployment cannot even configure the requester as an independent source: it is a wiring-time failure.
  - **Compatibility.** Omitted — or configured with no declared obligations — Kernel behaviour is byte-identical to this layer not existing: no resolution runs, the provider is not consulted, no result field appears, and the Governance Record and its digest are unchanged. The frozen v1 HTTP surface, the release manifest, the SDK surface and the compiled `dist/src/kernel/index.js` artifact are all untouched (`src/kernel/index.ts` gains type-only exports). Obligation state is *derived* on every evaluation rather than stored, so expiry needs no sweeper and repeated `enforce()` calls cannot double-discharge; what a production adapter must persist and guarantee is documented in the runtime README.
  - **Deliberately not included.** No bounded grant issuance, no grant attenuation, no approval routing, notification, scheduling, escalation, SLA, inbox, workflow engine, AI, ERP connector or policy DSL. Frontera understands "finance approval is required" and "a valid trusted finance approval has or has not been discharged"; obtaining it is the deployment's business.
- **`@aoc-enterprise/evidence-correlation`** (R004.J) — canonical, immutable `EnterpriseEvidenceCorrelation` contract representing the correlation graph linking the immutable business artifacts produced across a governed access lifecycle: `EnterpriseAccessDecision`, `EnterpriseAccessObligation` (`@aoc-enterprise/access-obligation`), `EnterpriseAccessGrant` (`@aoc-enterprise/access-grant`), `EnterpriseGrantRevocation` (`@aoc-enterprise/grant-revocation`), and `EnterpriseUsageEvent` (`@aoc-enterprise/usage-event`) — each referenced by an opaque identifier, never embedded. Declarative only — no evidence generation, no log collection, no provider execution, no auditing, no persistence, no runtime execution; it owns only the relationships between immutable records that already exist elsewhere. See `docs/architecture/ADR-EVIDENCE-CORRELATION.md` and the package README for the full design rationale, including why it deliberately cannot answer "was the provider successful?" or "did Pinata respond?".
- **`@aoc-enterprise/usage-event`** (R004.I) — canonical, immutable `EnterpriseUsageEvent` contract recording that a previously-issued `EnterpriseAccessGrant` (`@aoc-enterprise/access-grant`) was exercised: who, what, when, using which grant, against which resource, referenced by an opaque `grantRef` rather than embedded. Provider-neutral, closed usage-event vocabulary (`AccessAttempted`, `AccessStarted`, `AccessCompleted`, `AccessDenied`, `AccessExpired`, `AccessFailed`, `GrantConsumed`, `ContentViewed`, `ContentDownloaded`, `ContentStreamed`); declarative only — no authorization decision, no policy evaluation, no enforcement, no provider adapter, no provider success/failure status, no persistence, no runtime execution. See `docs/architecture/ADR-USAGE-EVENT.md` and the package README for the full design rationale, including why the contract deliberately cannot answer "was it allowed?", "was it enforced?", or "was it successful from the provider's perspective?".
- **`@aoc-enterprise/access-obligation`** (R004.F) — canonical, immutable `EnterpriseAccessObligation` contract representing a mandatory or optional condition attached to an evaluated `EnterpriseAccessDecision` (`@aoc-enterprise/access-decision`), referenced by an opaque `decisionRef` rather than embedded. Provider-neutral, closed obligation-type vocabulary (`require-approval`, `require-mfa`, `record-usage`, `watermark-content`, `read-only`, `time-limit`, `no-download`, `require-acceptance`); declarative only — no policy engine, no execution, no MFA, no watermarking, no download enforcement, no provider, no adapter, no grant. See `docs/architecture/ADR-POLICY-OBLIGATION.md` and the package README for the full design rationale, including why the existing `CanonicalObligation` (`@aoc-enterprise/canonical-runtime-contracts`), `EnterprisePolicyObligation` (`@aoc-enterprise/policy-runtime`), and `PolicyObligation` (`src/features/domain-policy-pack-runtime`) types were evaluated and not reused.

### Security
- **Fixed: `AocEnterprise.configuration` publicly exposed raw provider/application secrets (`authentication.apiKeys[].key`) to any holder of an `AocEnterprise` instance.** `createEnterprise()` assigned the full, secret-bearing `EnterpriseConfiguration` — including configured bearer API keys — directly to the public `configuration` field. Any caller (a direct property read, `JSON.stringify(enterprise.configuration)`, or an object spread of either `configuration` or the whole `enterprise` instance) could recover a configured secret in full. `AocEnterprise.configuration` is now typed as the new, redacted `PublicEnterpriseConfiguration` (see `src/enterprise/configuration/enterprise-configuration.ts`): every non-secret operational setting is preserved, and `authentication.apiKeys` is replaced by `authentication.apiKeyCount` and `authentication.apiKeyOrganizationScopes` (organization scoping only, never key values). The trusted in-process Node HTTP adapter — the one legitimate consumer that must compare a caller's bearer token against the real configured keys — now obtains the full configuration through a new, non-exported `getInternalEnterpriseConfiguration()` accessor keyed by instance identity (`composition-root.ts`), never through the public field. No other in-scope defect was found: a `DEFAULT_API_KEYS` symbol reported as a stable-surface export does not exist anywhere in this repository's history, and no source change was needed for that finding.
- **Fixed: `verifyCapabilityToken` (root-exported, `./crypto` subpath) previously returned `valid: true` for every capability token, including revoked and expired ones — a complete authorization bypass.** The function read `jti`, `trust_domain`, and `exp` off the token via an `as unknown as Record<string, unknown>` cast; none of those fields exist on the real `@aoc/protocol` `CapabilityToken` contract (the real fields are `tokenId`, `expiresAt`, and `revocationRefs`), so every guard condition was permanently unreachable and some malformed inputs (e.g. `null`) threw an uncaught `TypeError` instead of failing closed. The cast is removed; the function now validates against the real contract fields, revoked and expired tokens are correctly rejected, and malformed input returns `invalid` without throwing.
  - **Open gap — trust domain is not enforced.** The real `CapabilityToken` carries no trust-domain-bearing claim (the old `trust_domain` check never had a real field to read, on top of being misspelled), so it has been removed rather than reimplemented against an invented field or an unproven mapping (e.g. guessing `issuer` means trust domain). `CapabilityVerificationContext.trustDomain` is retained on the type to avoid a breaking signature change but is documented as unused and unenforced. Enforcing trust-domain isolation requires a product decision (e.g. adopting `@aoc/protocol`'s `TrustRegistryProvider`) that is out of scope for this fix — tracked as a follow-up.
  - **Open gap — signature verification is structural only, not cryptographic.** `CapabilityToken.proof` carries no signature bytes or key material, so `verifyCapabilityToken` can check proof *shape* (a recognized `proofType` with a non-empty `proofRef`) but not cryptographic integrity. Full tamper detection requires wiring `@aoc/protocol`'s `VerificationKeyResolver` port, which is out of scope for this fix — tracked as a follow-up.
  - **Open gap — revocation is checked against the caller-supplied `revokedJti` set only.** `CapabilityToken.revocationRefs` point at the protocol's `RevocationLookup` port, which Enterprise does not wire up anywhere; a token that declares `revocationRefs` this function cannot resolve now fails closed (`revocation_status_indeterminate`) rather than being silently treated as clear. Adopting `RevocationLookup` is out of scope for this fix — tracked as a follow-up.

## [1.2.1] — 2026-08-26

Protocol repin only. Frontera's active `@aoc/protocol` validation artifact moves from the **burned** `0.2.0-rc.0` candidate to the repaired successor `0.2.0-rc.1`. No Frontera behaviour, export, route or store schema changes.

### Security
- **Repinned to the repaired Protocol candidate; `@aoc/protocol@0.2.0-rc.0` is BURNED.** rc.0's canonical-JSON writer truncated exponent digits, so `canonicalizeJSON(7.9e-10)` and `canonicalizeJSON(7.9e-100)` both produced `"7.9e-1"` — two distinct numbers sharing one canonical form and therefore one digest (the collision is wider than the reported pair: `1.5e-300` collapsed to `"1.5e-3"`). Reproduced here against the exact burned artifact before the repin. Soberanía Protocol declared the candidate burned rather than repacking its bytes and cut `0.2.0-rc.1` from commit `eec79cdd4019dd42e1767909c5bd4e26d04c6f0f`, carrying its frozen integration contract from `aoc.cross-repository-integration@1.0.0` to `@1.0.1`. The rc.1 tarball was independently reproduced here from that pinned commit in a clean POSIX checkout through `scripts/protocol/build-protocol-tarball.mjs`: sha256 `b0d6ee6ff2010c4addab0bd683e2a89b9b2246f430c7e892fdc3d4123f3a3f60`, 280149 bytes, 407 files — matching Protocol's own evidence and byte-identical to the copy Live Data Rail vendored independently.
- **Frontera itself never bundled the defect.** The packed artifact ships no Protocol code (`files: ["dist"]`, and `@aoc/protocol` is an external peer dependency for every consumer), and this repin changes no compiled output — every `dist` checksum in `release/RELEASE_MANIFEST.json` is unchanged. What the burn invalidated is Frontera's *compatibility evidence*: candidates up to and including `1.2.0` were validated and handed off against an input later declared burned, so `1.2.0` is `SUPERSEDED_FOR_DOWNSTREAM_CONSUMPTION_DUE_TO_BURNED_PROTOCOL_INPUT` rather than defective.

## [1.2.0] — 2026-08-25

Security and correctness fixes to the durable Kernel Authority world introduced in 1.1.0. A post-merge review surfaced ten defects; six were reproduced against the merged code before any fix was written. Four contradicted guarantees 1.1.0 stated explicitly, so `1.1.0` should be treated as superseded rather than merely improved on.

### Security
- **Fixed: persisted authority events were not tamper-evident.** Reconstruction verified only that each event *cited* the previous event's stored digest; it never recomputed a digest from the event's own fields. Editing a capability token's `actions` and `resourceScopes` directly in the database — leaving every digest column untouched — was accepted, and the widened token hydrated as live authority (measured: `["read"]` over one scope became four actions over three scopes). Every event's digest is now recomputed from its own fields and compared on every read, through a single `computeKernelAuthorityEventDigest` shared by the writer and the verifier.
- **Fixed: a revocation lost from the end of a chain silently resurrected authority.** Sequence contiguity and digest linkage both still pass on a truncated chain, because the surviving prefix is perfectly self-consistent — and the last event of a chain is exactly where a revocation lives. Deleting only the final event returned a revoked actor as `active`. The reconstructed head is now cross-checked against the independently-written `latest_sequence`/`latest_event_digest` on the projection row, and a mismatch fails closed.
- **Fixed: the durable evaluation surface carried mutable authority handles.** `createDurableKernelProviders()` returned a set extending `KernelProviderSet`, which exposes the concrete Recognition and Authority runtimes — including `registerActor`, `issuePassport`, `issueCapabilityToken`, `registerRootIssuer` and `issueAuthorityGrant`. An application holding only that set could mint itself an actor and a covering token in the live world, name them in its request, and be ALLOWED, with no operator context and nothing recorded in the store. It now returns `DurableKernelDecisionService`, which carries a read-only provider, clock, id generator, store and `reload()` and no runtime handles at all; the handles stay private to the composition root via the unexported `createDurableKernelWorld`.
- **Fixed: an omitted organization was treated as an implicit match.** Only an explicit mismatch denied, so an otherwise-valid request with `organization` absent was evaluated against the configured organization's world and ALLOWED — which on the HTTP path also bypasses organization-scoped API-key authorization, since that check rejects only a mismatch. A caller could alternatively inject the id through free-form `context.organizationId`. The organization is now required (`RECOGNITION_ORGANIZATION_SCOPE_REQUIRED`), and the Kernel's request adapter strips the reserved `organizationId`/`organizationName` keys from the free-form context bag so the value can only ever come from the typed `organization` field.

### Fixed
- **A legitimately-provisioned authority world could permanently brick its own hydration.** Records were ordered by entity id within each kind, but authority grants may name a `parentGrantId` and delegation grants a `sourceAuthorityGrantId` that points at another delegation. A parent named `z-parent` with a child named `a-child` committed successfully and then failed *every* subsequent `reload()` and restart. Hydration now orders dependency-aware within each kind, preserving the incoming order everywhere else so a hydration stays reproducible across processes, and fails closed on a cycle rather than dropping the records involved.
- **`backup:v1` demanded the authority database from deployments that had disabled the feature.** Durable authority is opt-in and defaults to off, so those deployments have no `kernel-authority.sqlite` and never will — breaking previously-working backup automation on upgrade, with an error whose suggested remedy ("start the Host once") cannot apply to a disabled feature. The store is now part of the backup set only when `kernelAuthority.enabled` is true.
- **An expired credential that sorted first could shadow a valid one.** Selection preferred records whose *store* status was `active`, which says only "not revoked" — expiry lives in the payload. An actor holding a valid token could be denied because an expired one sorted earlier. Resolution now checks expiry against the provider clock, still falling back to a revoked or expired credential when only that one covers the action, so the denial names the real reason.
- **An idempotency key supplied on a replayed provision was never claimed**, leaving it free to be spent later on a different entity in the same organization, contrary to the documented one-key-one-payload rule. The claim is now recorded transactionally even when the entity operation itself replays.
- **`AOC_ENTERPRISE_KERNEL_AUTHORITY_REQUIRED=false` was inert.** The store was opened and the world hydrated before the lifecycle controller ever saw the module's criticality, so an unreadable authority database refused startup even when the deployment had declared the module optional. Criticality is now honoured at composition: `required` still fails startup, `optional` degrades to the empty fail-closed world (which denies everything) and reports an unhealthy module.
- **The durable contract could not express two restrictions the engine enforces.** `evidenceRequirements` and `approvalRequirement` were absent from `ProvisionCapabilityTokenInput` and were not replayed by hydration, so an approval- or evidence-gated token could not be persisted at all, and a structurally-compatible object carrying them would have had them silently discarded on reload. Both are now part of the contract and are replayed into the engine.

### Changed
- **`createDurableKernelProviders()` returns a narrower type.** `DurableKernelDecisionService` replaces the previous `KernelProviderSet`-extending shape; `DurableKernelProviderSet` remains exported as a deprecated alias. This is a breaking change to an API introduced in 1.1.0 and never published, and it is the fix for the self-authorization defect above rather than a refactor.
- **A request must now name its organization.** Also a behaviour change confined to the 1.1.0 durable path; the empty/default composition is unaffected.

### Versioning
- Package version `1.1.0` → `1.2.0`. The changed surface and behaviour are confined to the durable Kernel Authority capability added in 1.1.0, which was never published; `createDefaultKernelProviders()`, the frozen v1 HTTP surface, existing reason codes and every other export are untouched. Protocol stays pinned at `@aoc/protocol@0.2.0-rc.0`.

## [1.1.0] — 2026-08-24

Additive release: Frontera gains a durable, operator-provisioned authority source behind `AocKernel.evaluate()`. No breaking change; no existing behaviour altered for a deployment that does not opt in.

### Added
- **Durable Kernel Authority (P0-PKG-07)** — Frontera now owns a durable, operator-provisioned recognition/authority world, so an external application can obtain a real, independent, restart-surviving `AocKernel.evaluate()` decision without seeding Frontera on every request, becoming its own authority issuer, inventing capability tokens, or copying its permissions into Frontera at evaluation time. New Kernel Authority Store (`aoc.kernel-authority.schema.v1`, in-memory and SQLite, its own file and its own configured path — never inside the Governance, Evidence, Passport, Assurance or Governed Authority stores), append-only and digest-chained so historical authority records are never rewritten; `createDurableKernelProviders()` restores that world into unmodified Recognition Runtime / Authority Graph instances; `createKernelAuthorityProvisioningService()` is the trusted operator write surface, requiring a privileged `system` context plus a named operator on every write. Seven state families are persisted — actors, trust domains, passports, capability tokens, root issuers, authority grants, delegation grants — each proven necessary by executing the real engine; evidence ledgers, authority proofs, approval and handshake runtime state are deliberately not, because none of them changes what gets decided (see the ADR's state inventory). Evaluation is read-only with respect to authority source-of-truth: the provider set handed to an application carries no write surface and no operator context, so a request cannot register an actor, grant itself authority, expand its scope, issue itself a token, or un-revoke itself. Revocation is a terminal appended event and survives process restart and backup/restore; re-provisioning a revoked id is refused, so no retry ordering resurrects withdrawn authority. External application principals bind to Frontera actors through an explicit, uniquely-indexed `externalSubject` (`(organizationId, system, subjectId)`) that Frontera owns — never through an undocumented metadata key, and never by assuming an application user id *is* an actor id. Restart durability, revocation durability, cross-organization isolation and the no-self-provisioning control are proven in-process, across separate OS processes (`tests/durable-authority-process-restart.contract.test.mjs`), through backup/restore with the original state destroyed (`tests/durable-authority-portability.contract.test.mjs`), and in a clean-room consumer installing the packed tarball (`npm run check:clean-room-consumer`). New configuration: `AOC_ENTERPRISE_KERNEL_AUTHORITY_ENABLED` (default `false`), `_ORGANIZATION_ID`, `_SQLITE_PATH`, `_REQUIRED` (default `true` — an authority source that is silently absent is not a degraded feature). **Additive and opt-in:** `createDefaultKernelProviders()` keeps its real, empty, fail-closed world byte for byte, all existing reason codes and serialized evaluation shapes are unchanged, and a deployment that sets nothing new observes no behavioural difference. Soberanía Protocol is untouched: no Protocol change, no widened Protocol export, no invented Protocol capability. See `docs/enterprise/AOC_DURABLE_KERNEL_AUTHORITY.md` and `docs/architecture/ADR-DURABLE-KERNEL-AUTHORITY.md`.

### Changed
- **Backup and restore now cover four SQLite stores, not three.** `backup:v1`, `restore:v1`, `check:portability-smoke` and the clean-room drill all include the Kernel Authority Store. Its inclusion is not optional the way an audit store's would be: a recovery that restored evaluation history but not the authority world would come back with every actor unrecognized and every action denied. The portability comparison additionally re-evaluates against the restored world rather than only comparing rows — a restore that reproduced every row but decided differently would be a failed restore.

### Versioning
- Package version `1.0.0` → `1.1.0`. Additive public capability under SemVer (`docs/enterprise/API_STABILITY_V1.md`): new exports on the existing `./enterprise` subpath, no export removed or re-targeted, no breaking change. ## [1.0.0] — 2026-07-12

First production release. PR-008 is a hardening-only release: no new products, no new architecture, no functional behavior changes except fail-closed corrections listed below.

### Security (hardening; see `docs/security/SECURITY_HARDENING_V1.md`)
- **HTTP adapter fails closed on synchronous errors.** Auth rejections on passport/assurance routes, malformed percent-encoding in path segments, and invalid request URLs now return proper `401`/`400` error envelopes instead of raising uncaught exceptions.
- **Constant-time API-key matching.** Bearer tokens are compared via fixed-length SHA-256 digests with no early exit, removing the timing side channel; bearer parsing deduplicated into `orchestration/credential-matching.ts`.
- **Schema-version guards on all stores.** The Agent Passport and Assurance SQLite stores now refuse to open a database recorded under a different schema version (the Governance store already did). Rollback across schema versions requires restoring the matching backup.
- **Structured SQLite error classification.** Passport/assurance constraint violations are detected by `SQLITE_CONSTRAINT*` error codes instead of message-string sniffing.
- **Validated `busy_timeout` pragma** (positive safe integer) in all three stores; store error mappers now preserve the underlying error message; unhandled-error logs record the real route instead of a fixed label.
- **Schema-version check now runs before schema creation.** The Agent Passport and Assurance stores previously ran `CREATE TABLE IF NOT EXISTS` before checking the recorded schema version, so a refused foreign-schema database could still have this runtime's own (empty) tables created in it. The version is now checked first; a foreign-schema database is left untouched when refused (regression tests assert no mutation).
- **SDK `reactivatePassport` now posts the field the Host actually validates** (`reactivatedBy`, not `actorId`) — the method was unusable through the SDK before this fix.
- **SDK `IssuePassportRequest` type corrected** to mirror the real wire shape (nested `subject`/`organization` objects plus top-level `actorId`) instead of a flat shape that would deterministically fail Host validation.
- **Load test correctness phase now verifies concurrently-written records**, not a separate sequentially-seeded batch — a corrupted or dropped concurrent write would previously have been invisible to the correctness checks.

### Portability, backup & restore validation (see `docs/release/AOC_ENTERPRISE_V1_PORTABILITY_REPORT.md`)
- **`npm run backup:v1` / `npm run restore:v1`** — one official, fail-closed backup and restore command for the three independent SQLite stores, replacing the manual `sqlite3 .backup` procedure as the recommended default. Versioned backup format (`aoc.enterprise.backup.v1`), SHA-256 checksums, `PRAGMA integrity_check`, and schema-version compatibility are all validated before any file is copied; restore refuses to overwrite an existing target without `--force`, takes a pre-restore safety copy first, and rolls back on any post-restore verification failure.
- **`npm run validate:portability:v1`** — a fully automated clean-room drill: extracts the exact tracked commit via `git archive` outside the working tree, installs from the lockfile, builds, tests, seeds a synthetic fixture, backs it up, destroys the source stores, restores from the backup alone, proves full logical equivalence (Governance/Evidence/Passport/Assurance), and reruns the v1 release gate.
