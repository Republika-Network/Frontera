# Changelog

All notable changes to Soberanía Enterprise. The project follows [Semantic Versioning](https://semver.org/): the public HTTP API surface, the exported package entrypoints, and the store schema identifiers are the compatibility contract (see `docs/enterprise/API_STABILITY_V1.md`).

## [Unreleased]

### Added — P11 durable monetary outcomes and provider certainty
- **Every governed execution is durably recorded before and after its provider crossing.** New execution outcome store `src/enterprise/execution-outcome-store/` (port, in-memory, SQLite, validation, integrity, health module `aoc.enterprise.execution-outcomes`). Decision `docs/architecture/ADR-DURABLE-MONETARY-OUTCOMES.md`; invariants SEC-INV-102 … SEC-INV-110.
  - **Attempt, prepared before the write-ahead claim.** Holds the tenant, the evaluation, request, decision, grant and execution ids (references only), the action, and the exact P9 amount and asset the adapter receives. Preparation is idempotent, and a failure stops the request before the claim (`system_error` / `GOVERNED_ACTION_EXECUTION_CLAIM_FAILED`), so nothing is stranded.
  - **Initial observation, immutable.** Records `confirmed-completed`, `confirmed-not-completed` or `unconfirmed` (derived once from the runtime status via `providerEffectCertaintyOf`), the registry-authenticated attribution, an opaque `providerRef` and the closed failure reason. For a withheld execution it records the withholding layer and its codes instead. A different observation for the same execution is a conflict, never an overwrite. No adapter `detail` is persisted.
  - **Replay** answers from the observation with no provider call, and a replayed `executed` now returns its `providerRef`. Claim-only replays as `…_ALREADY_ATTEMPTED`, and so does an unreadable or corrupt record, never optimistically. Pre-P11 history still replays from the legacy Governance summary, and nothing is synthesized for it.
  - **Governance and P8.** The `execution_record` outcome row is now the compact summary of the canonical observation: it is written only after the observation, and its `digest` is the observation's. The write-ahead `attempt` row is unchanged. `outcomeRecorded` (result and P8 payload) now means the canonical observation is durable. P8 stays evidence only.
  - **Integrity.** SHA-256 over `aoc.canonical-json.v1`, verified on every read. This is integrity, not authenticity. SQLite uses `WAL` and `synchronous = FULL`, one `BEGIN IMMEDIATE` per write, and append-only triggers, and a schema-version guard (`aoc.execution-outcome-store.schema.v1`) refuses unknown files. Money is stored as `TEXT`.
  - **Composition.** Composed automatically with `governedActionOrchestrator`, which now requires it. It uses SQLite at `executionOutcome.sqlitePath` (`AOC_ENTERPRISE_EXECUTION_OUTCOME_SQLITE_PATH`, default `.data/execution-outcomes.sqlite`) under `persistence.provider = 'sqlite'`, and the process-local store otherwise. An unopenable store fails startup. Options: `createEnterprise({ executionOutcomes: { store } })` for a host-supplied store. Read-only surface: `AocEnterprise.executionOutcomes`. Not in portability v1 backup (P17), like the P7 ledger and the P8 stream.
- **`providerRef` on every provider certainty.** `ExecutionAdapterResult` `failed` / `unconfirmed` and `ExecutionOutcome` `execution-failed` / `execution-unconfirmed` gain an optional `providerRef` (additive). A reference never changes certainty. The new provider-neutral `isRecordableProviderRef` (execution runtime) filters references for every adapter: bounded printable ASCII, and no credential, JWT, PEM, URL, cookie or authorization shape. A non-string reference on `failed` / `unconfirmed` is dropped rather than turning the result into `ADAPTER_ERROR`. Generic HTTP keeps a safe configured reference on every actual response (completed, rejected, and unconfirmed 202 / 3xx / 408 / 5xx) and never fabricates one without a response. It now also omits URL-shaped values.
- **Reserved `assertedContext` keys:** `providerRef`, `providerStatus`, `providerCertainty`, `certainty`, `executionOutcome`, `executionStatus`, `outcomeRecorded`.
- **No endpoint, response field, status, reason code, SDK or schema-version change on existing stores.** No reconciliation, retry, polling, timer, receipt, settlement or rail-specific code.

### Changed — P10 authority-sourced payment ceilings and durable spending limits
- **The amount an actor asks to spend is no longer the source of the amount it is authorized to spend.** The Kernel grant projection (`sourceScopeFor`) no longer states an amount bound. The pre-P10 "Model A", where the grant source ceiling was the request's own amount, is retired. Decision `docs/architecture/ADR-AUTHORITY-SOURCED-PAYMENT-CEILINGS.md`; invariants SEC-INV-094 … SEC-INV-101.
  - **Durable monetary authority in the existing Kernel Authority Store.** `ProvisionAuthorityGrantInput.constraints` and `ProvisionDelegationGrantInput.constraints` (additive, optional) carry the Authority Graph's existing `max_amount` (now enforced) and a new `spending_limit` (`limitId`, `currency`, `maximum`, `window: lifetime | rolling`). Constraints are:
    - validated on append by both stores, at provisioning against the trusted asset registry, and on hydration (malformed → the world fails closed);
    - covered by the existing event digest;
    - replayed into the Authority Graph unchanged.

    No new store, table or schema version.
  - **Issuance.** For a host-classified financial action, the issuance core:
    1. resolves the monetary authority on the lineage proven by the decision's own `AuthorityProof`;
    2. proves the requested amount does not exceed the ceiling (otherwise `financial-authority-withheld` / `FINANCIAL_AUTHORITY_CEILING_EXCEEDED`, with no grant, reservation or adapter call);
    3. attaches the authority's ceiling (`withGrantAmountCeiling`);
    4. re-resolves the authority inside the synchronous commit guard;
    5. commits to it in `authorityBindingDigest` (`grantAuthorityProvenanceDigest`).

    Publicly this is `withheld` / `authority-binding` with a new `FINANCIAL_AUTHORITY_*` reason code; the wire union is unchanged. The Kernel decision is never rewritten.
  - **P7.** For a financial exercise, the authority's `spending_limit`s are appended to the host policy's answer under stable authority-anchored buckets and admitted in the same atomic reservation. A colliding host bucket is `EXERCISE_CONTROL_POLICY_INVALID`. Exercise-time binding revalidation also recomputes the financial authority, so revoked, narrowed or replaced authority withholds before any reservation. P7's settle, release and window semantics are unchanged.
  - **Composition.** `createEnterprise` wires the resolver (`createKernelFinancialAuthorityResolver`) over the hydrated authority world when governed actions and exercise controls are both composed. `financialAuthority` is not a host option. New reserved `assertedContext` keys: `max_amount`, `paymentCeiling`, `ceiling`, `spendingLimit`, `spendingLimits`, `spending_limit`, `budgetId`, `remaining`, `financialAuthority`, `authorityLimit`, `authorityRef`, `constraints`.
  - **Behavioural change.** A financial action now needs:
    - provisioned `max_amount` and `spending_limit` on the actor's authority lineage;
    - composed P7 exercise controls;
    - an actor whose recognition consults the Authority Graph (agents, or actors acting for a principal).

    Otherwise it is withheld at issuance. Pre-P10 financial grants (binding-only provenance) are withheld at exercise until they expire; non-financial grants are byte-identical to before.
  - **No new endpoint, SDK method, schema version or migration.**

### Changed — P9 canonical monetary semantics (v1 wire kept, exactly)
- **Money is exact text with an explicit asset on the governed financial-action spine.** New pure module `src/features/monetary-runtime`: one canonical decimal form and its `BigInt` compare/add (P7's `exercise-decimal.ts` now delegates to it — one implementation), a frozen trusted asset registry (`{ assetId, scale }`, no aliases, namespaced identifiers such as `xrpl:USD/rIssuer`), the single amount ingress `parseMonetaryAmount`, and the host-trusted `FinancialActionClassifier`. Decision `docs/architecture/ADR-CANONICAL-MONETARY-SEMANTICS.md`; invariants SEC-INV-089 … SEC-INV-093.
  - **The v1 wire is kept, exactly.** `POST /api/governed-actions` (`amount.value`) and `POST /api/governance/evaluate` (`action.amount`) still accept a JSON number — now read from its exact source characters via the platform's JSON source-text access (`src/enterprise/api/exact-monetary-json.ts`), never through a double — and additively accept decimal text. Excess precision for the asset's trusted scale is rejected, never rounded; an unknown asset is rejected (existing `400` / `GOVERNED_ACTION_INTENT_INVALID`). SDK `GovernedActionAmount.value` widens additively to `string | number`. An already-parsed JavaScript number handed in-process to `AocEnterprise.governAction` has no source text and is refused.
  - **Policy-pack thresholds are canonical text.** `payments-basic` and `sports-event-settlement-basic` state `'10000'` / `'5000'`; `PolicyPackValidator` refuses a number or non-canonical threshold on `amount` (`INVALID_MONETARY_THRESHOLD`); the evaluator compares text with text only; a non-canonical input amount is `invalid_input` (fail closed). No production function converts a number into monetary text (the retired conversion is P7 test support only).
  - **Host-trusted classification.** New composition option `monetary: { assets, financialActions }`, built once and handed — as the same instances — to the governed-action boundary and the P7 gate. A financial action requires a strictly positive amount; any other action may carry none. `financial`, `actionClass`, `classification`, `scale` and `assetScale` are reserved `assertedContext` keys. Omitted, nothing is financial and every amount-bearing intent is rejected.
  - **Text end to end.** `ActionDescriptor.amount`, `GrantCeilingBound.limit`, `GrantBoundEvaluation.limit`, `GrantExerciseAmount.value`, `ExerciseControlQuery.amount.value` and the policy-pack `amount` fields are `string`. Grant ceilings compare exactly and never across assets; the Generic HTTP adapter keeps its P6 body contract (`amount.value` a JSON number) with the token written exactly from canonical text via `JSON.rawJSON`.
  - **P7.** The gate requires the host classifier (`actionClassifier`, no default), classifies the grant's action, exposes `query.actionClass`, and adds `EXERCISE_CONTROL_ACTION_CLASS_MISMATCH`; the number-to-decimal conversion is gone from the gate path.
  - **Persistence: no migration.** Pre-P9 grant rows with a numeric ceiling are read back unchanged and cover no amount (fail closed until they expire); Governance Records are not rewritten (a replay against a numeric-amount record is an idempotency conflict); ledger usage was already canonical text. No schema version changes.

### Security
- **P8 revocation event order preserved (independent review).** Fix-forward; no API, SDK, schema-version, endpoint, vocabulary or identity change.
  - **A revocation can no longer be overtaken by the facts it precedes.** Attributing a revocation to its lifecycle needs a read of the authoritative grant, and that read previously ran on a chain of its own — so a later fact for the same grant (an execution outcome, say) could be appended first, and the stream could show an effect recorded before the revocation that caused it. Every fact carrying a `boundedGrantId` now passes through that grant's **intake chain** in report order, with the attribution read as a step of that chain: a slow read holds that grant's own evidence behind it — a projector-side barrier — and nothing else, and no authority path waits for it. The committed decision carries no grant and still goes straight to its stream. Exact per-lifecycle ordering assertions are restored; the sorted-membership weakening is gone.
  - **The non-blocking claim is narrowed to what the code proves.** `SEC-INV-088` and the P8 docs now state that *durable projection is not part of authority control flow*: an asynchronous append that is slow, unreachable or never settles cannot hold a decision, the claim-to-adapter crossing, a reservation or a revocation. They no longer imply latency or thread isolation — projection shares the process and the event loop, `better-sqlite3`'s `BEGIN IMMEDIATE` append (lock wait, `fsync`) is synchronous work on it, and a synchronous or slow store can still add process latency. Worker isolation is explicitly out of Stage A.
  - **Tests.** Slow-attribution ordering regression (issuance and claim established, attribution held, revocation then outcome reported, the outcome append proven *not* invoked, attribution released, `grant.revoked` invoked before `execution.outcome.observed`, final sequence and digest chain verified); every grant-scoped fact after a pending revocation waits in its own report order; a stuck attribution holds only its own grant; a completed lifecycle drains to `pending: 0`; exact ordering restored in the governed-action and P7 revocation scenarios.
- **P8 evidence projection decoupled from execution (independent review).** Fix-forward; no API, SDK, schema-version, endpoint or event-vocabulary change (28 endpoints; SDK `1.1.0`; root stays `1.6.0`).
  - **Reporting a fact no longer awaits its projection.** `AuthorityEventRecorder` and `ExerciseControlObserver` methods now return `void`: an authority-bearing module builds a bounded fact, hands it over and continues. The previous shape awaited a `Promise<void>` inside a `try`/`catch`, which handled a *rejected* projection and nothing at all about a *pending* one — a stuck store could have held a committed decision before its grant was issued, sat between the durable write-ahead claim and the adapter crossing, kept a P7 reservation consuming while `admit()` never returned (P7 has no TTL or sweeper), or withheld a revocation's confirmation. The argument "we await it but catch errors, therefore it cannot affect the path" is removed from the docs and the tests along with the code.
  - **The projector owns ordering.** One serial chain per stream — event N+1's append is not invoked until N's has settled — so removing the `await` cannot race a stream's writes; chains are per key, so a stuck lifecycle holds only itself; an idle chain still starts on a microtask, so no store work (including a synchronous `better-sqlite3` transaction) runs inside the reporting call's own stack frame. The store keeps sequence, previous digest, `recordedAt` and the digest. No timer, worker, retry scheduler or sweeper was added.
  - **Queue depth is visible:** projector health and the `aoc.enterprise.authority-event-stream` module gain `pending`. Operator signal only — no authority path reads it or waits on it.
  - **Tests.** Never-settling regressions on the real governed path for the decision, claim, reservation (settle and release), revocation and outcome projections; queue-order and independent-stream regressions; a never-settling observer against the P7 gate; structural scans inverted to fail the build on any `await` of a recorder, observer or report helper, and on any recorder method that is not `void`.
  - `SEC-INV-088` (EVENT-STREAM-09); threat model §7.20 gains the "evidence becoming a control-flow dependency" row; the completeness limit (a failed or still-queued projection is never retried or reconciled) is now stated explicitly wherever integrity is claimed.

## [1.6.0] — 2026-09-22

Additive release. The governed-action / bounded-grant lifecycle becomes **reconstructable afterwards**: a canonical, durable, append-only, ordered, hash-chained and tenant-confined **authority event stream** records each lifecycle fact strictly after it is established in its authoritative store — and nothing that decides ever reads it. Also ships the post-merge P7 exercise-control hardening. No new endpoint, request or response field, status, reason code or SDK change.

### Added
- **Canonical authority event stream (P8, Stage A) — composed with `governedActionOrchestrator`.** Evidence (layer F), never authority. Design `docs/enterprise/AOC_CANONICAL_AUTHORITY_EVENT_STREAM.md`; decision `docs/architecture/ADR-CANONICAL-AUTHORITY-EVENT-STREAM.md`; source `src/enterprise/authority-event-stream/`.
  - **Closed vocabulary, facts only.** `governance.decision.committed` (after commit **and** re-read + verification, every status), `grant.issued`, `grant.revoked`, `grant.expiry.observed` (an observation at the grant's own `expiresAt` when an assessment finds it expired — no timer, no sweeper, no persisted transition), `execution.attempt.claimed` (the write-ahead claim this call appended), `exercise.reservation.reserved` / `.settled` / `.released` (what the P7 ledger returned), `execution.outcome.observed` (`executed`, `execution-failed` with its reason, `execution-unconfirmed`, `withheld` with its layer and codes — certainty never collapsed; adapter attribution; bounded `providerRef` as evidence only). Withholdings before a grant exists, uncommitted decisions and raw transport input produce no event.
  - **Identity and order.** One stream per governed-action request per organization (`aoc.aes:` from organization + server-derived request id); deterministic event ids (`aoc.aev:` from stream, type and source artifact id) through the Governance Store's `computeDigest` (`aoc.canonical-json.v1`) — no second canonicalization. Contiguous per-stream sequence from 1, genesis = the committed decision, each event chained to the previous digest; `occurredAt` from the authoritative artifact, `recordedAt` from the store's injected clock. Same id + same fact → the recorded event; same id + different fact → `AUTHORITY_EVENT_CONFLICT`, never last-write-wins. Replays add no event.
  - **Durable store** (`aoc.authority-event-stream.schema.v1`) at `authorityEventStream.sqlitePath` / `AOC_ENTERPRISE_AUTHORITY_EVENT_STREAM_SQLITE_PATH` (default `.data/authority-event-stream.sqlite`) under `persistence.provider = 'sqlite'`, process-local otherwise, or a host-supplied `authorityEventStream.store` (never closed by the Host): WAL, `synchronous = FULL`, one `BEGIN IMMEDIATE` transaction per append that verifies the whole stream and its sealed head before choosing head + 1, `UNIQUE (stream_id, sequence)`, append-only triggers, unknown schema refused before mutation, corruption reported and never repaired.
  - **Evidence cannot become authority.** Lifecycle code reaches the stream only through the write-only `AuthorityEventRecorder` (type-only, in the orchestrator and ACE) and the P7 gate's write-only `ExerciseControlObserver`; every method returns `Promise<void>` and every call site discards failure. A failing, corrupt or unopenable stream changes no decision, grant, revocation, reservation, routing, adapter invocation or result, and the optional `aoc.enterprise.authority-event-stream` module reports it (`degraded` / `unhealthy`) without taking the Host out of `ready`.
  - **Read surface.** `AocEnterprise.authorityEventStream` — read + verify only, tenant-scoped, verify-first — for trusted in-process code. No route, no SDK method. The Enterprise barrel exports P8 **types only**.
  - `ExecutionLedger.claim` now reports the instant written on the claim row (internal).
- **Security inventory.** `SEC-INV-080` … `SEC-INV-087` (EVENT-STREAM-01…08, path- or component-local); threat model §7.20; asset A-29; the no-bypass inventory stays eight of fifty-three (the stream's appends are evidence persistence folded into EP-049 and EP-013, not a new effect path).
- **Tests.** Domain (vocabulary, identity, digest input, closed contract, unsafe values, certainty rules, chain verification), one shared store contract on the in-memory and SQLite stores, SQLite restart / triggers / schema / seventeen raw corruption cases, worker-thread races (unique, duplicate and conflicting facts; chain verified after every round), the real governed-action path for every outcome and P7 fact, replay, projection failure never becoming authority (no stream vs failing store vs throwing recorder, byte-identical), composition / degradation / ownership / tenancy, full-Host secret leakage with a Generic HTTP adapter, and structural boundaries.

### Security
- **P7 exercise-control hardening (post-merge independent review).** Fix-forward; no API, SDK, schema-version or endpoint change (28 endpoints; SDK `1.1.0`, 5 runtime exports, 0 dependencies).
  - **The reservation instant is the ledger's admission instant.** `ExerciseReservationRequest` no longer carries `reservedAt`; the ledger samples its injected clock once inside its atomic admission critical section — in SQLite as the first statement of the `BEGIN IMMEDIATE` callback, after the write lock is held — and uses that one instant for the rolling-window threshold, `reserved_at`, `reserved_at_ms`, every rule row's `reserved_at_ms` and the returned `ExerciseReservationRecord`. Previously the gate recorded the pre-lock assessment instant, so a reservation that waited on the write lock could age out of a rolling window early. `createInMemoryExerciseControlLedger` now takes `{ now }`; the composition root hands the SQLite ledger the same clock as the grant assessment. A ledger clock that answers a non-instant fails admission closed.
  - **The grant is re-read after the reservation.** With exercise controls composed the order is now grant read #1 → containment #1 → emergency #1 → binding #1 → policy → reservation → **grant read #2 → containment #2 at a fresh injected-clock instant** → binding #2 (`ExerciseControlGate.revalidate`, synchronous, against the second read) → emergency #2 → adapter → settle | release. A grant that expired, was revoked, became unreadable or corrupt, or no longer covers the attempt while the reservation waited is withheld as `grant-exercise` with its existing `GRANT_EXERCISE_*` codes and the reservation is released (retained if the release cannot be recorded). The validated action and the reported assessment and instant come from the second read. Binding #2 moved out of `admit()` into `revalidate()`.
  - **Rolling admission verifies before it filters.** The SQLite ledger no longer range-filters a rolling bucket on the unverified `reserved_at_ms` column before integrity validation; it verifies every reservation the `(limit_id, scope_key)` index names and applies the window to the verified instant. A rule row whose `reserved_at_ms` alone is moved backwards without re-sealing now fails admission closed (`EXERCISE_CONTROL_LEDGER_STATE_CORRUPT` → `EXERCISE_CONTROL_LEDGER_UNAVAILABLE`) instead of silently returning capacity. The accepted residual that allowed it is removed. Admission is now linear in a bucket's full indexed history.

### Not included
- System-wide event coverage (Stage A is path-local to governed actions), a public read API, webhooks, SSE, Kafka / NATS / Redis Streams, global or cross-tenant ordering, cross-region replication, distributed consensus, exactly-once, WORM, signatures / KMS / HSM (P12), retention or cleanup, portability v1 backup of the stream file, model convergence with `EnterpriseUsageEvent` / `EnterpriseEvidenceCorrelation` (P9), XRPL.
- **No HTTP API change:** 28 endpoints, unchanged. **No SDK change:** `@aoc-enterprise/enterprise-host-sdk` stays `1.1.0`, 5 runtime exports, 0 runtime dependencies.

## [1.5.0] — 2026-09-21

Additive release. Repeated use of a bounded grant becomes governable: **aggregate count, aggregate amount and rolling-velocity limits**, admitted through a **durable, atomic reservation before the provider is reached**, with conservative settlement and **exercise-time revalidation of the grant's authority binding** — opt-in, path-local to bounded-grant execution, and additional narrowing only. No new endpoint, request field, status, `withheldBy` value or SDK change.

### Added
- **Exercise controls (P7) — `authorityControlledExecution.exerciseControls`.** Trusted host composition: a synchronous `policy` (required), a synchronous `revalidateAuthorityBinding` resolver (required) and an optional `ledger`. Design `docs/enterprise/AOC_EXERCISE_CONTROLS.md`; decision `docs/architecture/ADR-EXERCISE-AGGREGATE-CONTROLS.md`.
  - **Immutable grant + separate authoritative ledger.** `BoundedGrant` gains no usage counter; consumption lives in the exercise-control ledger (`src/features/exercise-control-runtime`, durable in `src/enterprise/exercise-control-ledger`), kept apart from Governance Store evidence.
  - **Closed limit contract.** `count` and `amount` metrics over `lifetime` or `rolling` (1 s – 1 year) windows; ≤ 32 limits; duplicate `(limitId, scopeKey)` refused; bounded `limitId` / `scopeKey`; the policy's answer is validated into a frozen snapshot on every exercise and an invalid one withholds.
  - **Exact amounts.** Canonical decimal text, one conversion from the attempt's number, `BigInt` arithmetic; exact units, no conversion; no float accumulation and no SQL aggregate over a floating column.
  - **Reservation before effect.** Deterministic reservation id; request, policy and binding fingerprints; `reserved` and `settled` consume, `released` does not; `execution-unconfirmed` settles; `execution-failed` and post-reservation withholdings release; a failure to finalize keeps consuming and never rewrites the outcome; no expiry, sweeper or startup cleanup; one execution identity is one attempt.
  - **Durable SQLite ledger** (`aoc.exercise-control-ledger.schema.v1`) at `exerciseLedger.sqlitePath` / `AOC_ENTERPRISE_EXERCISE_LEDGER_SQLITE_PATH` (default `.data/exercise-ledger.sqlite`), opened only when P7 is composed and no ledger is supplied: WAL, `synchronous = FULL`, `BEGIN IMMEDIATE` admission, append-only triggers, row / rule / terminal-event / bucket-head digests validated on every counted read, unknown schema refused before mutation; closed on shutdown only when the composition opened it. An `aoc.enterprise.exercise-control` module reports its health.
  - **Exercise-time authority-binding revalidation.** ACE grants now carry an opaque `authorityBindingDigest` (canonical SHA-256 of the binding resolved and commit-proved at issuance; the commit-boundary equality check is unchanged). With P7 composed, the current binding must match it exactly, before and after the reservation; a grant without it is withheld as unverifiable.
  - **Gate ordering.** grant read → containment → emergency → binding #1 → policy → reservation → binding #2 → emergency re-check → adapter → settle | release, with one finalization exit whose disposition is exhaustive over `ExecutionOutcome`.
- **`EXERCISE_CONTROL_REASON_CODES`** — nine codes, disjoint from every other vocabulary. Internal `ExecutionOutcome` gains `withheld / withheldBy: 'exercise-control'` (assessment still usable); the public result maps it to the existing `withheldBy: 'exercise'`. The governed-action evidence ledger records `withheld:exercise-control:<CODE>…` and replays it; historical rows read unchanged.
- **`BoundedGrant.authorityBindingDigest?`** — optional and additive: pre-P7 grants keep their canonical bytes, deterministic ids and digests, and their SQLite rows reopen unchanged.
- **Reserved `assertedContext` keys** extended with the P7 names; the same names are undeclared (rejected) intent fields.
- **Security inventory.** `SEC-INV-070` … `SEC-INV-079` (EXERCISE-CTRL-01…10, path- or component-local); effect paths **EP-051 … EP-053** (reserve / settle / release — local authority-state writes inside the gate, `PROVEN — PATH LOCAL`), moving the headline count to eight of fifty-three; asset A-28; threat model §7.19; baseline M-6 **proven path-local for the P7-enabled path only**. SEC-INV-U06 stays unimplemented system-wide.
- **Tests.** Domain, shared ledger contract (in-memory and SQLite), SQLite persistence / crash / corruption / schema, worker-thread concurrency races, execution-gate ordering and finalization, authority-binding and bounded-grant backward compatibility, governed-action mapping / replay / Generic HTTP outcomes / caller-quota rejection at zero Kernel, ledger, DNS and socket activity, composition, and structural boundaries.

## [1.4.0] — 2026-09-21

Additive release. The governed execution path can now produce a **real external HTTP effect** through a pinned, SSRF-resistant Generic HTTP Execution Adapter composed by the operator — with no new endpoint, no new request field, no SDK change, and an explicit, durable "unconfirmed" outcome for effects whose completion cannot be established.

### Added
- **Generic HTTP Execution Adapter (P6, Stage A) — `executionAdapterRouting.genericHttpAdapters`.** A deterministic translator, `ValidatedExecutionAction + trusted configuration → one pinned HTTPS request`, composed by `createEnterprise` as an ordinary child of the **existing** execution adapter registry. Not a proxy, fetch endpoint, router, policy engine or second authorization layer. Source `src/enterprise/execution-adapters/generic-http/`; design `docs/enterprise/AOC_GENERIC_HTTP_EXECUTION_ADAPTER.md`.
  - **The caller may describe the action, never the network effect.** Origin, method, path segments, query, headers, flat JSON body and credential are closed, declarative operator configuration (no callbacks, templates, expressions or JSONPath), validated, snapshotted and frozen at composition — **before any store is opened**, so bad configuration fails startup. Undeclared keys at any level (`followRedirects`, `proxy`, `agent`, `lookup`, `allowPrivateNetwork`, `rejectUnauthorized`, …) are refused, never ignored. Mapping sources are exactly `subject`, `action`, `resource`, `counterparty`, `organization`, `amount.value`, `amount.unit`, `notAfter` and `correlation.*`; `boundedGrantId` and `assertedContext` are not sources. Required sources default to true and a missing one stops the request before any I/O. Path values are single encoded segments.
  - **Pinned HTTPS origin, SSRF and DNS-rebinding defence.** `https://` + DNS hostname + optional port only; IP literals, `localhost`/local-only names, userinfo, path, query and fragment refused. Every execution re-resolves the hostname, rejects the whole answer if any address is not publicly routable (special-purpose IPv4 incl. cloud metadata; IPv6 allow-list `2000::/3` minus reserved blocks; mapped/compatible/NAT64/6to4/Teredo refused), and binds the one approved IP to the socket through a hostname-ignoring `lookup` over `node:https` with `agent: false`; SNI, certificate verification and `Host` stay on the pinned hostname. TLS verification is hardcoded on: the transport sets `rejectUnauthorized: true` explicitly, so an ambient `NODE_TLS_REJECT_UNAUTHORIZED=0` cannot relax it, and no option, host setting or environment variable can.
  - **One attempt.** At most one outbound request per `execute()`; no redirects (every 3xx is `unconfirmed` — its effect is uncertain — and `Location` is never read), no retries, no proxy, no connection reuse. The response body is never read; `providerRef` comes only from one configured response header (single value, ≤ 512 chars) and is never dereferenced. Credentials (bearer or one explicit header) are operator configuration only and never appear in results, records, the ledger, logs, events, health or errors. Bounds: URL 8 KiB, 64 query fields, 32 headers, 64 body fields, 64 KiB body, 4 KiB header value, 16 KiB total headers, timeout 100 ms–60 s (default 10 s).

  - **The invariant: no external execution through the grant-aware path without a successful exercise check.** No grant, unknown grant, expired grant, revoked grant, tampered grant, wrong subject, wrong action, wrong resource, wrong counterparty, wrong tenant, amount above the ceiling, correlation mismatch — every one withholds the adapter. The property under test is never "the assessment said no", it is **the adapter was not called**: the suite counts invocations, asserting `0` for every blocked row and `1` for a valid exercise.
  - **Authorization and exercise are two moments, so they are two calls.** `authorize()` evaluates through the Kernel and then issues a bounded grant; `exercise()` re-reads the authoritative grant, proves the attempted action is inside it, and only then reaches a provider. A grant issued at T+0, exercised at T+5m, expiring at T+10m and revocable at any point between is observable at each step, which folding the two together would have destroyed.
  - **The authorization decision is never rewritten.** Every outcome carries the `KernelEvaluationResult` exactly as the Kernel produced it. `decision = ALLOW` with `exercise = BLOCKED` and `executor = NOT CALLED` is the normal, intended combination for an expired or revoked grant, and the historical decision stays `allowed` permanently. Asserted for expiry, for revocation, for a pending blocking obligation, and for a `DENY` that stays a `DENY`.
  - **`AocKernel.evaluate()` and `AocKernel.enforce()` are unchanged.** No accepted ADR gives grants a role in the executor gate; the ADR's own gate on execution is the *obligation* gate layer D already implements. Making a configured grant capability withhold `enforce()`'s executor would have invented a lifecycle semantic the architecture does not state, so grant-aware execution is a separate, explicitly-composed path and the Kernel remains the authority-control orchestrator and the only decision producer.
  - **The authority validity ceiling is a hard gate at the composition root, closing the `validityCeilings: []` wiring hazard.** An empty ceiling list is correct for a genuinely unbounded upstream authority, but it cannot distinguish "none exists" from "the host forgot to pass one" — and in the second case a grant could silently outlive the mandate justifying it. A new typed `GrantAuthorityBinding` makes the composition root state which world it is in: `{ kind: 'bounded-authority', authorityKind, authorityRef, expiresAt }` or `{ kind: 'no-temporal-authority-bound', sourceKind, justification }`. There is no third option and no default — the bounded arm does not compile without a real instant, and the permissive arm costs an explicit source kind and justification, so it cannot be reached by omission. `resolveAuthorityBinding` is a **required** composition option (asserted by a `@ts-expect-error` proof), and a resolver that returns nothing or returns a malformed binding fails closed with its own `AUTHORITY_BINDING_*` vocabulary — no grant, and never mistaken for a policy denial or a grant refusal.
  - **Exercise-time validation, deterministic and fail-closed on twelve checks.** Request well-formedness, grant existence in the authoritative store, canonical digest integrity, expiry against an injected clock, revocation, subject, four-field correlation, and action/resource/counterparty/organization/amount containment. Every failing reason is reported rather than only the first. Containment uses `compareGrantBound` — the same closed algebra issuance attenuates with — so `incomparable` (shape mismatch, unparseable value, differing currency) is treated exactly as `broader`. Absence on either side is a refusal: a grant bounding an axis the attempt leaves unstated, and an attempt asserting an axis the grant never bounded, are both refused, because containment cannot be proven against an absent bound.
  - **The grant is read, never received.** `GrantExerciseRequest` carries a grant *reference* and has no field for a grant object, scope, expiry, revocation status, digest or grant-claimed subject — a bounded grant is an internal record a caller never holds, so it never presents one. The authoritative store is re-read on every attempt, with no cache and no fast path, so a revocation committed a millisecond ago is visible to the very next exercise and no sweeper is load-bearing. A tampered stored grant whose ceiling was raised to 10000 is refused entirely rather than honoured at either value.
  - **Model A is unchanged at exercise time.** A 7500 grant issued off a request for 7500, under a rule reading `amount <= 10000`, refuses an attempted 9000 *and* an attempted 10000. The policy threshold is never reusable authority, and a grant is never a reusable policy envelope — that artifact is a mandate.
  - **Upstream authority is deliberately not re-read at exercise time**, on the accepted precedent rather than for effort: `ADR-GOVERNED-AUTHORITY-RESERVATION.md` settles that an issued artifact is "an authorization artifact in its own right" and must not "smuggle a dynamic lineage dependency back in". A grant's lifetime was contained by the authority ceiling at issuance and re-proven inside the commit boundary, so `grant.expiresAt <= authority.expiresAt` is a standing invariant and the read-time expiry check enforces it transitively. A deployment that wants an authority change to end a live grant sooner revokes the grant — a recorded, correlated, immediate act.
  - **The commit boundary re-resolves the authority binding, not just the decision.** `resolveAuthorityBinding` is synchronous so the store can call it inside its critical section with no `await` between the read that decides and the write that records. A mandate shortened from T+30m to T+6m, or revoked outright, between the caller's measurement and the commit refuses the issuance and writes nothing — asserted by making the world really move between the two, never faked with a comment.
  - **A fourth reason-code vocabulary, asserted disjoint from the other three.** `GRANT_EXERCISE_REASON_CODES` is a separate constant, in a separate file, with a separate type, and every value carries the `GRANT_EXERCISE_` prefix. "This grant could not be issued" and "this grant cannot cover this action" send an operator to different places, so they are never the same code — and neither is ever a policy `DENY`.
  - **The provider adapter receives a validated action and nothing else.** `ExecutionAdapter.execute(ValidatedExecutionAction)` gets the grant id, the subject and horizon **read from the trusted store**, the already-proven action/resource/counterparty/tenant/amount, the request/decision/execution correlation and an opaque payload reference. It receives no grant, scope, digest, source authorization, decision, status, reason code, policy result, obligation state or context fact — a test asserts the absence of each, because an adapter that could re-decide would be a second decision producer. An adapter that throws becomes `ADAPTER_ERROR` rather than escaping, and `execution-failed` is a distinct status from `withheld` so a provider outage is never reported as an authority problem.
  - **No consumption model, and repeated exercise is preserved.** Every accepted ADR is silent on single-use, counters, remaining uses, nonce consumption and replay ledgers, and `ADR-ACCESS-LIFECYCLE.md` says the opposite for the record *about* use — usage events are "many per `grantRef`, repeatable by design". Two exercises of one valid grant both run, and the stored grant is byte-identical afterwards. A structural test refuses the vocabulary so one cannot be smuggled in later.

The composition layer additionally constructs no decision, never reads `decision.status`, never calls `enforce()`, and never instantiates a Kernel.

  - **Persistence, stated as a limitation rather than assumed away.** The default bounded-grant store remains in memory, so grants do not survive a process restart. That is acceptable for this vertical slice because a lost grant reads as `GRANT_EXERCISE_NOT_FOUND` and withholds the adapter — losing a grant is always the closed direction — and because `ADR-ACCESS-LIFECYCLE.md` states that an issued, unexercised grant is not an error state. A deployment whose grants must outlive a restart supplies its own `BoundedGrantStorePort`; the port already documents the seven guarantees a durable adapter must provide. No new schema, database architecture or store identifier is introduced.
  - **Evidence correlation preserved without building the Evidence phase.** `request → decision → obligation → grant → exercise → execution result → revocation/expiry` stays reconstructible: the four-field grant correlation is stable, the grant carries `sourceDigest` and `digest`, and every execution outcome — withheld ones included — carries the request id, decision id, execution id, grant id, assessment and a stable `exercisedAt` from the injected clock. No event stream, no behavioural analytics, no risk scoring.
  - **Four hardening fixes from review, each with a regression test.** (1) The clock is sampled **after** the authoritative store read, never before it: a durable read beginning one millisecond before `expiresAt` and completing at `expiresAt` would otherwise judge the grant at an instant that had already passed and let an expired grant reach the provider. The test reproduces it by advancing the clock inside the store's own `read`. (2) The free-form `payloadRef` channel is **removed** from both the exercise request and the validated action — an adapter dereferencing an opaque handle would execute data no bound covered and no assessment saw, so a grant for 7500 to V123 could submit a payload for 100000 to V999 with all twelve checks passing; resolving it here would make this layer read provider data, and integrity-binding it would mean choosing a binding scheme no accepted ADR defines, so the action *is* the payload and a structural test keeps any such channel out. - **Grant Runtime (layer E) — attenuation-only bounded grants, derived from an authorized, obligation-satisfied decision.** Implements the second half of `docs/architecture/ADR-OBLIGATION-DISCHARGE-AND-BOUNDED-GRANT.md` (§4–§6): an authorization that concluded *allow* and whose blocking obligations are satisfied can now be turned into a strictly bounded, inspectable, deterministic authority artifact that says what portion of that authority may be exercised, by whom, against what, under which bounds, and until when. See `src/features/grant-runtime/README.md`.
  - **The settling invariant: `GRANT ⊆ AUTHORIZED AUTHORITY`.** A grant may preserve, narrow, shorten, lower or reduce a bound; it may never widen one. Enforced in types, in a service and in tests rather than in documentation: `compareGrantBound` is total over a closed algebra of four bound shapes (`identity`, `set`, `ceiling`, `window`) and answers `equal`/`narrower`/`broader`/`incomparable`; `attenuateGrantScope` permits the first two and refuses the other two; and `grantScopeIsWithin` re-derives the invariant *of the issued artifact*, independently of the function that produced it. A table-driven suite enumerates, per bound shape, a source bound and the four positions a requested bound can take relative to it. If ⊆ cannot be *proven*, no grant is issued — there is no third direction.
  - **ALLOW does not mean a grant exists, and a withheld grant does not mean DENY.** An allowed authorization with a blocking obligation outstanding reports `status: 'allowed'` with `grants.eligibility: 'ineligible'` and no grant; a denied authorization with every obligation satisfied reports `status: 'denied'` with `grants.eligibility: 'ineligible'` and no grant. Neither rewrites the decision, and nothing in the layer can: `assessGrantEligibility` receives a projection carrying no status to rewrite. ADR §3.
  - **Fail-closed in four places.** A requested bound broader than its source, incomparable to it (different shape, different unit, unparseable instant), on an axis the source never stated, or carrying the wrong shape for its axis — each refuses the whole grant. A source silent on an axis is never read as "unbounded, so anything is narrower".
  - **Subject semantics: no delegation.** A grant's holder is the subject the source authorization was evaluated for; a different holder is refused with `GRANT_SUBJECT_INVALID`. No accepted ADR defines delegation for grants, so the default posture is the closed one and no field can express otherwise.
  - **Expiry is a state derived from an injected clock at read time**, never from a sweeper having run (ADR §6, hard invariant 7). No timer, no job, and no `Date.now()` anywhere in the layer — a structural test fails the build if one appears. A malformed horizon makes a grant unusable rather than usable-forever.
  - **Grant validity: the issuer proposes, the ceilings contain.** `expiresAt` is finite, strictly after `issuedAt`, and supplied by the trusted issuer through `GrantIssuanceRequest.expiresAt` — never derived from deployment configuration, never defaulted, and never read from caller-controlled request data. It is then contained by every applicable upstream ceiling that exists: the decision's validity bound if it carries one, the governing mandate or representative authority's window where one applies, and the deployment's **optional** safety cap where one is configured. The effective ceiling is the minimum of those, and a request above it is **refused, never silently clamped** — one rule, no special case by which ceiling was strictest; a refusal names the ceiling that capped it. No decision record in this repository carries a validity window, so `validityCeilings` is frequently empty; an empty list is an ordinary answer and never means unbounded, because the issuer must still state a finite expiry. Authority ceilings are re-proven **inside the store transaction**, so a mandate whose window shortens between measurement and commit refuses the issuance rather than committing a grant that would outlive it. ADR §4, "Where a grant's validity comes from", and hard invariants 9 and 10.
  - **`maximumGrantLifetimeSeconds` is an optional deployment safety cap, not the source of validity.** Its absence is not a reason to withhold a grant: `{ declaration: {} }` is a valid configuration and still issues grants. A *present* value that is zero, negative or non-finite is rejected when the Kernel is wired, not when a payment is evaluated.
  - **Validity is not a scope axis.** A scope says what a grant may act over; a validity window says when. `expiresAt` is a top-level field on the grant, exactly as it is on `EnterpriseAccessGrant`, rather than a bound inside `GrantScope` — which would have made a grant carry both an inherited ceiling and its own expiry, the second independently-settable source of truth `ADR-ACCESS-GRANT.md` refuses. Grant identity is derived from the correlation, the subject, the canonical bounds **and** the accepted expiry.
  - **Revocation reuses the existing architecture rather than creating a second one.** The same closed seven-value vocabulary as `ENTERPRISE_GRANT_REVOCATION_REASONS` (`ADR-GRANT-REVOCATION.md`), asserted identical by test. A revocation is an immutable event held beside the grant, not a mutable status on it — extending `ADR-ACCESS-GRANT.md`'s own reasoning for excluding `'expired'` from a status vocabulary. Deterministic, correlated to grant identity, idempotent (a second revocation returns the first unchanged and never re-dates it), and fail-safe. **It never changes the historical authorization**: a decision that concluded allow concluded allow, permanently; only exercisability changes.
  - **Usage and replay are deliberately not implemented.** Every accepted ADR is silent on single-use, multi-use, usage count, consumption and replay for grants, so this phase implements issuance, validity and revocation and invents no consumption model. `BoundedGrant` carries no counter; adding one is a new decision and a new ADR.
  - **Transactional issuance, against the world as it is at commit.** `BoundedGrantStorePort.issue` takes a *synchronous* `commitGuard` called inside the store's critical section, after the records it decides on have been read there — ADR §4.6 and hard invariant 6, the commit-boundary discipline `ADR-GOVERNED-CONSTRAINT-APPLICABILITY.md` §3 established for `acquireReservation`. A dedicated suite makes the world really move between the caller's measurement and the commit (the obligation becomes unsatisfied, the authorization stops permitting exercise, the source authority narrows, the authorization disappears, a revocation lands) and asserts the refusal in each case. Duplicate and concurrent-equivalent issuance of one identity produce one grant, never two.
  - **Evaluation is not issuance.** `AocKernel.evaluate()` reports whether an authorization *would be* grant-eligible and what such a grant would be bounded by, touches no store and creates no artifact; issuance is a separate operation through `createGrantIssuanceService`, under the authoritative store's commit boundary. The repository already separates the two everywhere (`preflight` vs `enforce`, `resolveAvailability` vs `acquireReservation`) and this phase keeps that line.
  - **`enforce()` is unchanged, deliberately.** No accepted ADR gives grants a role in `enforce()`; the ADR's own gate on execution is the obligation gate, which layer D already implements and this phase leaves exactly as it found it. What the enforcement cases require is a read-time exercisability check, and `assessExercise` provides it — `unusable` for an expired, revoked, tampered or unknown grant, with a broader-than-authority grant unable to exist at all. Wiring it into an execution path is the execution-adapter phase's work.
  - **Deterministic identity and canonical integrity.** `boundedGrantId` is derived from the correlation, the subject, the canonical bounds and the accepted expiry, and from nothing else — no UUID, no counter, no clock, no randomness — so a replay produces a byte-identical artifact and duplicate issuance collides rather than duplicates. The canonical serialization is pinned **byte-equal** to the Governance Store's `aoc.canonical-json.v1` by test rather than by prose (layer E may not import layer F), and `grant.digest` matches the repository's existing `computeDigest` idiom. A grant edited after issuance no longer matches its digest and is refused at read time. This is integrity, not a signature: cryptographic signing and any external token format (JWT, macaroon, UCAN, OAuth, capability token) are deferred to signer integration, and a structural test refuses the vocabulary outright.
  - **Caller security boundary.** A public requester cannot self-issue or broaden a grant, for two independent and separately tested reasons: nothing reads a caller's grant claim (the source authorization is projected from the typed request and the Kernel's own decision id; the narrowing is host input; `KernelEvaluationRequest` has no grant field and there is no route), and `aoc.grant` is a reserved namespace stripped from the free-form context bag whether or not the capability is configured — the third application of the rule `request-adapter.ts` applies to `organizationId`, `aoc.context` and `aoc.obligations`. An adversarial suite submits `{"grant":{"maxAmount":1000000}}`, `{"aoc.grant":{"action":"*"}}`, `{"grantEligible":true}`, `{"grant":{"expiresAt":"2099-01-01T00:00:00Z"}}` and `{"grant":{"subject":"attacker"}}`, and asserts the entire grant evaluation is byte-identical with and without them.
  - **Layer boundaries, structurally.** The grant runtime imports neither layer C nor layer D, never the Kernel, the Enterprise Host, the Governance Store or the legacy runtime; it reaches no network, filesystem, database, ledger, signer, wallet or provider; it contains no `eval`, no `new Function`, no dynamic import and no AI or intelligence dependency; and `GRANT_REASON_CODES` is asserted disjoint from both the authorization and the obligation-exercise vocabularies, so "grant issuance failed" can never be encoded as a policy `DENY`.
  - **Compatibility.** Omitted, Kernel behaviour is byte-identical to this layer not existing: no eligibility is assessed, no result field appears, no namespace reaches policy, and the Governance Record is unchanged. Configured, the authorization half of the result is still byte-identical — the grant step adds a field and reads no `status`, `reasonCodes`, `summary` or `policies`, asserted against the function's own source. The frozen v1 HTTP surface (34 routes / 27 endpoints), `release/api-surface.v1.json`, the release manifest, the SDK surface and the compiled `dist/src/kernel/index.js` artifact are all untouched; `src/kernel/index.ts` gains type-only exports. `@aoc/protocol` is untouched, no store schema identifier changes, and no existing package is modified.
  - **Model A, not Model B.** "The evaluated scope" a grant attenuates is the scope of the evaluated request and the decision taken on it, never the envelope of whichever policy rule matched. A 7500 payment allowed by a rule reading `amount <= 10000` yields a source ceiling of **7500**; a requested 9000 or 10000 is refused, and a table-driven suite asserts every case. Nothing carries a rule's threshold out of policy evaluation — `EnforcementPolicyPackEvaluationResult` has no quantity field at all — so the narrower reading is the only one the records support. A reusable authority envelope with a ceiling and a window is a **mandate**, not a grant.
  - **Deliberately not included.** No execution or exercise path, no cryptographic signing, no token format, no Evidence extension, no usage/consumption model, no delegation, no durable grant store (the port's production guarantees are documented instead), no decision-carried validity bound (a decision-contract change, not a layer E change), no extension of the frozen `packages/access-grant` contract, no binding of the existing Sovereign Access `AccessGrantService.issueGrant` to a verified decision, no XRPL, no signer, no wallet, no workflow engine, no notifications and no AI.
- **Obligation Runtime (layer D) — a deterministic discharge lifecycle for obligations, with no change to any authorization decision.** Implements `docs/architecture/ADR-OBLIGATION-DISCHARGE-AND-BOUNDED-GRANT.md`'s first half: `require-approval` stops being, in the ADR's words, "a statement the platform makes and never keeps". A declared obligation gains a closed lifecycle, a discharge gains provenance, and an action the Kernel authorized *conditionally* does not execute until the condition is met. See `src/features/obligation-runtime/README.md`.
  - **The invariant, and the whole point.** An obligation never changes the meaning of an authorization decision. An allowed action whose blocking obligation is undischarged reports `status: 'allowed'` alongside `obligations.exerciseEligibility: 'blocked'`, and the executor does not run — it is never rewritten into a denial. ADR §3: collapsing the two "would erase the distinction between 'policy said no' and 'policy said yes, conditionally, and the condition was not met'". Settled by deletion rather than by inspection: one request is evaluated with no capability and at four lifecycle states, and the authorization half of the result is byte-identical every time.
  - **The lifecycle.** Six states — `required`, `pending`, `discharged`, `verified`, `waived`, `expired` — and the eight legal transitions between them, transcribed from the ADR's tables. `verified` and `waived` satisfy a blocking obligation; `required`, `pending`, `discharged` and `expired` do not; `verified`, `waived` and `expired` are terminal. Illegal transitions are reported, never repaired: a terminal obligation is not reopened, and an out-of-order observation does not rewrite history. `required` is a layer D state — B declares that an obligation is required, D materializes the instance in `required` and manages it from there.
  - **A failed verification has no state of its own.** A verification attempt that does not succeed leaves the obligation `discharged` and records why on the instance; the record never changes state or satisfaction. ADR §2.
  - **Expiry is a declared deadline, not discharge staleness.** An obligation may declare an optional `expiresAt` on its requirement, from operator configuration and never from caller-controlled request data. Against an injected clock, at read time, an obligation at or past it in `required`, `pending` or `discharged` becomes `expired`; one that declares no deadline never expires; and expiry never disturbs `verified` or `waived`.
  - **`verified` is not `discharged`.** A discharge reported by a source the deployment classifies as self-reporting reaches `discharged` and stops there; only an *independent* source — an approval runtime, a provider adapter, a verified attestation — reaches `verified`, and only `verified` and `waived` satisfy a blocking obligation. The class comes from operator configuration and from nowhere else: `ObligationDischargeObservation` has no `verificationClass` field, no `state` field, and no way to acquire either through the port.
  - **Kernel integration.** `ObligationDischargeProvider` is a fifth optional port alongside `policyPackProvider`, `governedAuthorityProvider`, `governedConstraintProvider` and `contextResolution`. `evaluate()` reports the lifecycle, the blocking aggregate and the exercise eligibility; `enforce()` withholds the executor and reports `execution.withheldBy: 'obligation'` over an untouched decision. Obligation state never reaches the policy input — the dependency runs `D reads B`, never back — so no policy rule can turn on whether an obligation was discharged.
  - **Security boundary.** A caller cannot discharge its own obligation. Obligation state has exactly one producer, the configured provider, and `ObligationDischargeQuery` carries no requester bag, so nothing a caller sends is ever consulted; the `aoc.obligations` namespace is stripped from the free-form context bag regardless. An adversarial suite submits the forgeries a caller would actually try — `financeApproved: true`, `obligation.state: 'DISCHARGED'`, a fabricated `aoc.obligations` — plus discharges citing an unregistered source, the wrong obligation, the wrong request, the wrong action and a stale window, and none of them opens the gate. A deployment cannot even configure the requester as an independent source: it is a wiring-time failure.
  - **Compatibility.** Omitted — or configured with no declared obligations — Kernel behaviour is byte-identical to this layer not existing: no resolution runs, the provider is not consulted, no result field appears, and the Governance Record and its digest are unchanged. The frozen v1 HTTP surface, the release manifest, the SDK surface and the compiled `dist/src/kernel/index.js` artifact are all untouched (`src/kernel/index.ts` gains type-only exports). Obligation state is *derived* on every evaluation rather than stored, so expiry needs no sweeper and repeated `enforce()` calls cannot double-discharge; what a production adapter must persist and guarantee is documented in the runtime README.
  - **Deliberately not included.** No bounded grant issuance, no grant attenuation, no approval routing, notification, scheduling, escalation, SLA, inbox, workflow engine, AI, ERP connector or policy DSL. Frontera understands "finance approval is required" and "a valid trusted finance approval has or has not been discharged"; obtaining it is the deployment's business.
- **`@aoc-enterprise/evidence-correlation`** (R004.J) — canonical, immutable `EnterpriseEvidenceCorrelation` contract representing the correlation graph linking the immutable business artifacts produced across a governed access lifecycle: `EnterpriseAccessDecision`, `EnterpriseAccessObligation` (`@aoc-enterprise/access-obligation`), `EnterpriseAccessGrant` (`@aoc-enterprise/access-grant`), `EnterpriseGrantRevocation` (`@aoc-enterprise/grant-revocation`), and `EnterpriseUsageEvent` (`@aoc-enterprise/usage-event`) — each referenced by an opaque identifier, never embedded. Declarative only — no evidence generation, no log collection, no provider execution, no auditing, no persistence, no runtime execution; it owns only the relationships between immutable records that already exist elsewhere. See `docs/architecture/ADR-EVIDENCE-CORRELATION.md` and the package README for the full design rationale, including why it deliberately cannot answer "was the provider successful?" or "did Pinata respond?".
- **`@aoc-enterprise/usage-event`** (R004.I) — canonical, immutable `EnterpriseUsageEvent` contract recording that a previously-issued `EnterpriseAccessGrant` (`@aoc-enterprise/access-grant`) was exercised: who, what, when, using which grant, against which resource, referenced by an opaque `grantRef` rather than embedded. Provider-neutral, closed usage-event vocabulary (`AccessAttempted`, `AccessStarted`, `AccessCompleted`, `AccessDenied`, `AccessExpired`, `AccessFailed`, `GrantConsumed`, `ContentViewed`, `ContentDownloaded`, `ContentStreamed`); declarative only — no authorization decision, no policy evaluation, no enforcement, no provider adapter, no provider success/failure status, no persistence, no runtime execution. See `docs/architecture/ADR-USAGE-EVENT.md` and the package README for the full design rationale, including why the contract deliberately cannot answer "was it allowed?", "was it enforced?", or "was it successful from the provider's perspective?".
- **`@aoc-enterprise/access-obligation`** (R004.F) — canonical, immutable `EnterpriseAccessObligation` contract representing a mandatory or optional condition attached to an evaluated `EnterpriseAccessDecision` (`@aoc-enterprise/access-decision`), referenced by an opaque `decisionRef` rather than embedded. Provider-neutral, closed obligation-type vocabulary (`require-approval`, `require-mfa`, `record-usage`, `watermark-content`, `read-only`, `time-limit`, `no-download`, `require-acceptance`); declarative only — no policy engine, no execution, no MFA, no watermarking, no download enforcement, no provider, no adapter, no grant. See `docs/architecture/ADR-POLICY-OBLIGATION.md` and the package README for the full design rationale, including why the existing `CanonicalObligation` (`@aoc-enterprise/canonical-runtime-contracts`), `EnterprisePolicyObligation` (`@aoc-enterprise/policy-runtime`), and `PolicyObligation` (`src/features/domain-policy-pack-runtime`) types were evaluated and not reused.

### Security
- **Fixed: `AocEnterprise.configuration` publicly exposed raw provider/application secrets (`authentication.apiKeys[].key`) to any holder of an `AocEnterprise` instance.** `createEnterprise()` assigned the full, secret-bearing `EnterpriseConfiguration` — including configured bearer API keys — directly to the public `configuration` field. Any caller (a direct property read, `JSON.stringify(enterprise.configuration)`, or an object spread of either `configuration` or the whole `enterprise` instance) could recover a configured secret in full. `AocEnterprise.configuration` is now typed as the new, redacted `PublicEnterpriseConfiguration` (see `src/enterprise/configuration/enterprise-configuration.ts`): every non-secret operational setting is preserved, and `authentication.apiKeys` is replaced by `authentication.apiKeyCount` and `authentication.apiKeyOrganizationScopes` (organization scoping only, never key values). The trusted in-process Node HTTP adapter — the one legitimate consumer that must compare a caller's bearer token against the real configured keys — now obtains the full configuration through a new, non-exported `getInternalEnterpriseConfiguration()` accessor keyed by instance identity (`composition-root.ts`), never through the public field. No other in-scope defect was found: a `DEFAULT_API_KEYS` symbol reported as a stable-surface export does not exist anywhere in this repository's history, and no source change was needed for that finding.
- **Fixed: `verifyCapabilityToken` (root-exported, `./crypto` subpath) previously returned `valid: true` for every capability token, including revoked and expired ones — a complete authorization bypass.** The function read `jti`, `trust_domain`, and `exp` off the token via an `as unknown as Record<string, unknown>` cast; none of those fields exist on the real `@aoc/protocol` `CapabilityToken` contract (the real fields are `tokenId`, `expiresAt`, and `revocationRefs`), so every guard condition was permanently unreachable and some malformed inputs (e.g. `null`) threw an uncaught `TypeError` instead of failing closed. The cast is removed; the function now validates against the real contract fields, revoked and expired tokens are correctly rejected, and malformed input returns `invalid` without throwing.
  - **Open gap — trust domain is not enforced.** The real `CapabilityToken` carries no trust-domain-bearing claim (the old `trust_domain` check never had a real field to read, on top of being misspelled), so it has been removed rather than reimplemented against an invented field or an unproven mapping (e.g. guessing `issuer` means trust domain). `CapabilityVerificationContext.trustDomain` is retained on the type to avoid a breaking signature change but is documented as unused and unenforced. Enforcing trust-domain isolation requires a product decision (e.g. adopting `@aoc/protocol`'s `TrustRegistryProvider`) that is out of scope for this fix — tracked as a follow-up.
  - **Open gap — signature verification is structural only, not cryptographic.** `CapabilityToken.proof` carries no signature bytes or key material, so `verifyCapabilityToken` can check proof *shape* (a recognized `proofType` with a non-empty `proofRef`) but not cryptographic integrity. Full tamper detection requires wiring `@aoc/protocol`'s `VerificationKeyResolver` port, which is out of scope for this fix — tracked as a follow-up.
  - **Open gap — revocation is checked against the caller-supplied `revokedJti` set only.** `CapabilityToken.revocationRefs` point at the protocol's `RevocationLookup` port, which Enterprise does not wire up anywhere; a token that declares `revocationRefs` this function cannot resolve now fails closed (`revocation_status_indeterminate`) rather than being silently treated as clear. Adopting `RevocationLookup` is out of scope for this fix — tracked as a follow-up.

## [1.2.0] — 2026-08-25

Security and correctness fixes to the durable Kernel Authority world introduced in 1.1.0. A post-merge review surfaced ten defects; six were reproduced against the merged code before any fix was written. Four contradicted guarantees 1.1.0 stated explicitly, so `1.1.0` should be treated as superseded rather than merely improved on.

### Security
- **Fixed: persisted authority events were not tamper-evident.** Reconstruction verified only that each event *cited* the previous event's stored digest; it never recomputed a digest from the event's own fields. Editing a capability token's `actions` and `resourceScopes` directly in the database — leaving every digest column untouched — was accepted, and the widened token hydrated as live authority (measured: `["read"]` over one scope became four actions over three scopes). Every event's digest is now recomputed from its own fields and compared on every read, through a single `computeKernelAuthorityEventDigest` shared by the writer and the verifier.
- **Fixed: a revocation lost from the end of a chain silently resurrected authority.** Sequence contiguity and digest linkage both still pass on a truncated chain, because the surviving prefix is perfectly self-consistent — and the last event of a chain is exactly where a revocation lives. Deleting only the final event returned a revoked actor as `active`. The reconstructed head is now cross-checked against the independently-written `latest_sequence`/`latest_event_digest` on the projection row, and a mismatch fails closed.
- **Fixed: the durable evaluation surface carried mutable authority handles.** `createDurableKernelProviders()` returned a set extending `KernelProviderSet`, which exposes the concrete Recognition and Authority runtimes — including `registerActor`, `issuePassport`, `issueCapabilityToken`, `registerRootIssuer` and `issueAuthorityGrant`. An application holding only that set could mint itself an actor and a covering token in the live world, name them in its request, and be ALLOWED, with no operator context and nothing recorded in the store. It now returns `DurableKernelDecisionService`, which carries a read-only provider, clock, id generator, store and `reload()` and no runtime handles at all; the handles stay private to the composition root via the unexported `createDurableKernelWorld`.
- **Fixed: an omitted organization was treated as an implicit match.** Only an explicit mismatch denied, so an otherwise-valid request with `organization` absent was evaluated against the configured organization's world and ALLOWED — which on the HTTP path also bypasses organization-scoped API-key authorization, since that check rejects only a mismatch. A caller could alternatively inject the id through free-form `context.organizationId`. The organization is now required (`RECOGNITION_ORGANIZATION_SCOPE_REQUIRED`), and the Kernel's request adapter strips the reserved `organizationId`/`organizationName` keys from the free-form context bag so the value can only ever come from the typed `organization` field.

### Fixed
- **A legitimately-provisioned authority world could permanently brick its own hydration.** Records were ordered by entity id within each kind, but authority grants may name a `parentGrantId` and delegation grants a `sourceAuthorityGrantId` that points at another delegation. A parent named `z-parent` with a child named `a-child` committed successfully and then failed *every* subsequent `reload()` and restart. Hydration now orders dependency-aware within each kind, preserving the incoming order everywhere else so a hydration stays reproducible across processes, and fails closed on a cycle rather than dropping the records involved.
- **`backup:v1` demanded the authority database from deployments that had disabled the feature.** Durable authority is opt-in and defaults to off, so those deployments have no `kernel-authority.sqlite` and never will — breaking previously-working backup automation on upgrade, with an error whose suggested remedy ("start the Host once") cannot apply to a disabled feature. The store is now part of the backup set only when `kernelAuthority.enabled` is true.
- **An expired credential that sorted first could shadow a valid one.** Selection preferred records whose *store* status was `active`, which says only "not revoked" — expiry lives in the payload. An actor holding a valid token could be denied because an expired one sorted earlier. Resolution now checks expiry against the provider clock, still falling back to a revoked or expired credential when only that one covers the action, so the denial names the real reason.
- **An idempotency key supplied on a replayed provision was never claimed**, leaving it free to be spent later on a different entity in the same organization, contrary to the documented one-key-one-payload rule. The claim is now recorded transactionally even when the entity operation itself replays.
- **`AOC_ENTERPRISE_KERNEL_AUTHORITY_REQUIRED=false` was inert.** The store was opened and the world hydrated before the lifecycle controller ever saw the module's criticality, so an unreadable authority database refused startup even when the deployment had declared the module optional. Criticality is now honoured at composition: `required` still fails startup, `optional` degrades to the empty fail-closed world (which denies everything) and reports an unhealthy module.
- **The durable contract could not express two restrictions the engine enforces.** `evidenceRequirements` and `approvalRequirement` were absent from `ProvisionCapabilityTokenInput` and were not replayed by hydration, so an approval- or evidence-gated token could not be persisted at all, and a structurally-compatible object carrying them would have had them silently discarded on reload. Both are now part of the contract and are replayed into the engine.

### Changed
- **`createDurableKernelProviders()` returns a narrower type.** `DurableKernelDecisionService` replaces the previous `KernelProviderSet`-extending shape; `DurableKernelProviderSet` remains exported as a deprecated alias. This is a breaking change to an API introduced in 1.1.0 and never published, and it is the fix for the self-authorization defect above rather than a refactor.
- **A request must now name its organization.** Also a behaviour change confined to the 1.1.0 durable path; the empty/default composition is unaffected.

### Versioning
- Package version `1.1.0` → `1.2.0`. The changed surface and behaviour are confined to the durable Kernel Authority capability added in 1.1.0, which was never published; `createDefaultKernelProviders()`, the frozen v1 HTTP surface, existing reason codes and every other export are untouched. Protocol stays pinned at `@aoc/protocol@0.2.0-rc.0`.

## [1.1.0] — 2026-08-24

Additive release: Frontera gains a durable, operator-provisioned authority source behind `AocKernel.evaluate()`. No breaking change; no existing behaviour altered for a deployment that does not opt in.

### Added
- **Durable Kernel Authority (P0-PKG-07)** — Frontera now owns a durable, operator-provisioned recognition/authority world, so an external application can obtain a real, independent, restart-surviving `AocKernel.evaluate()` decision without seeding Frontera on every request, becoming its own authority issuer, inventing capability tokens, or copying its permissions into Frontera at evaluation time. New Kernel Authority Store (`aoc.kernel-authority.schema.v1`, in-memory and SQLite, its own file and its own configured path — never inside the Governance, Evidence, Passport, Assurance or Governed Authority stores), append-only and digest-chained so historical authority records are never rewritten; `createDurableKernelProviders()` restores that world into unmodified Recognition Runtime / Authority Graph instances; `createKernelAuthorityProvisioningService()` is the trusted operator write surface, requiring a privileged `system` context plus a named operator on every write. Seven state families are persisted — actors, trust domains, passports, capability tokens, root issuers, authority grants, delegation grants — each proven necessary by executing the real engine; evidence ledgers, authority proofs, approval and handshake runtime state are deliberately not, because none of them changes what gets decided (see the ADR's state inventory). Evaluation is read-only with respect to authority source-of-truth: the provider set handed to an application carries no write surface and no operator context, so a request cannot register an actor, grant itself authority, expand its scope, issue itself a token, or un-revoke itself. Revocation is a terminal appended event and survives process restart and backup/restore; re-provisioning a revoked id is refused, so no retry ordering resurrects withdrawn authority. External application principals bind to Frontera actors through an explicit, uniquely-indexed `externalSubject` (`(organizationId, system, subjectId)`) that Frontera owns — never through an undocumented metadata key, and never by assuming an application user id *is* an actor id. Restart durability, revocation durability, cross-organization isolation and the no-self-provisioning control are proven in-process, across separate OS processes (`tests/durable-authority-process-restart.contract.test.mjs`), through backup/restore with the original state destroyed (`tests/durable-authority-portability.contract.test.mjs`), and in a clean-room consumer installing the packed tarball (`npm run check:clean-room-consumer`). New configuration: `AOC_ENTERPRISE_KERNEL_AUTHORITY_ENABLED` (default `false`), `_ORGANIZATION_ID`, `_SQLITE_PATH`, `_REQUIRED` (default `true` — an authority source that is silently absent is not a degraded feature). **Additive and opt-in:** `createDefaultKernelProviders()` keeps its real, empty, fail-closed world byte for byte, all existing reason codes and serialized evaluation shapes are unchanged, and a deployment that sets nothing new observes no behavioural difference. Soberanía Protocol is untouched: no Protocol change, no widened Protocol export, no invented Protocol capability. See `docs/enterprise/AOC_DURABLE_KERNEL_AUTHORITY.md` and `docs/architecture/ADR-DURABLE-KERNEL-AUTHORITY.md`.

### Changed
- **Backup and restore now cover four SQLite stores, not three.** `backup:v1`, `restore:v1`, `check:portability-smoke` and the clean-room drill all include the Kernel Authority Store. Its inclusion is not optional the way an audit store's would be: a recovery that restored evaluation history but not the authority world would come back with every actor unrecognized and every action denied. The portability comparison additionally re-evaluates against the restored world rather than only comparing rows — a restore that reproduced every row but decided differently would be a failed restore.

### Versioning
- Package version `1.0.0` → `1.1.0`. Additive public capability under SemVer (`docs/enterprise/API_STABILITY_V1.md`): new exports on the existing `./enterprise` subpath, no export removed or re-targeted, no breaking change. New runtime component version (Kernel Authority Runtime 1.0.0) and store schema identifier (`aoc.kernel-authority.schema.v1`), both recorded in `release/RELEASE_MANIFEST.json`. The frozen v1 HTTP surface is unchanged — this increment adds no route — and the Protocol dependency stays pinned at `@aoc/protocol@0.2.0-rc.0`.

## [1.0.0] — 2026-07-12

First production release. PR-008 is a hardening-only release: no new products, no new architecture, no functional behavior changes except fail-closed corrections listed below.

### Security (hardening; see `docs/security/SECURITY_HARDENING_V1.md`)
- **HTTP adapter fails closed on synchronous errors.** Auth rejections on passport/assurance routes, malformed percent-encoding in path segments, and invalid request URLs now return proper `401`/`400` error envelopes instead of raising uncaught exceptions.
- **Constant-time API-key matching.** Bearer tokens are compared via fixed-length SHA-256 digests with no early exit, removing the timing side channel; bearer parsing deduplicated into `orchestration/credential-matching.ts`.
- **Schema-version guards on all stores.** The Agent Passport and Assurance SQLite stores now refuse to open a database recorded under a different schema version (the Governance store already did). Rollback across schema versions requires restoring the matching backup.
- **Structured SQLite error classification.** Passport/assurance constraint violations are detected by `SQLITE_CONSTRAINT*` error codes instead of message-string sniffing.
- **Validated `busy_timeout` pragma** (positive safe integer) in all three stores; store error mappers now preserve the underlying error message; unhandled-error logs record the real route instead of a fixed label.
- **Schema-version check now runs before schema creation.** The Agent Passport and Assurance stores previously ran `CREATE TABLE IF NOT EXISTS` before checking the recorded schema version, so a refused foreign-schema database could still have this runtime's own (empty) tables created in it. The version is now checked first; a foreign-schema database is left untouched when refused (regression tests assert no mutation).
- **SDK `reactivatePassport` now posts the field the Host actually validates** (`reactivatedBy`, not `actorId`) — the method was unusable through the SDK before this fix.
- **SDK `IssuePassportRequest` type corrected** to mirror the real wire shape (nested `subject`/`organization` objects plus top-level `actorId`) instead of a flat shape that would deterministically fail Host validation.
- **Load test correctness phase now verifies concurrently-written records**, not a separate sequentially-seeded batch — a corrupted or dropped concurrent write would previously have been invisible to the correctness checks.
