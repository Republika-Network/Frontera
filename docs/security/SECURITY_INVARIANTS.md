## 1. Purpose

This document defines, for every security property Frontera claims:

1. **the guarantee** — what is actually true;
2. **the scope** — the exact path, layer, component or boundary it holds within;
3. **the enforcement mechanism** — how it is prevented from regressing;
4. **the evidence** — the file, line, or test that proves it;
5. **the boundary** — where the guarantee stops being true;
6. **the implementation status** — enforced, partially enforced, or not implemented.

It exists because the repository's guarantees are unusually strong **within specific paths** and absent outside them. Stating a path-local guarantee without its scope is the most likely way this project would accidentally overclaim. Every entry below therefore carries a scope, and the scope is part of the invariant — not a footnote to it.

`docs/kernel/AOC_KERNEL_INVARIANTS_V1.md` remains authoritative for the Kernel's own ten decision-engine invariants and is not superseded by this document; it is Kernel-scoped, and this document is the cross-cutting artifact that places it alongside every other guarantee.

## 2. Security Model

Three distinctions govern how this repository reasons about authority.

```
Intelligence  !=  Authority     an actor that can determine what to do has not thereby been permitted to do it
Capability    !=  Permission    an actor that can technically reach an effect has not thereby been authorized to produce it
Intent        !=  Mandate       an actor's declared purpose is not a grant; a mandate is held by a trusted store, not asserted by the actor
```

The security objective is **not** "prevent an agent from ever becoming malicious." It is:

> prevent malicious intent from automatically obtaining legitimate authority or technical capability to produce privileged effects.

That objective has two halves, and this repository is strong in one and absent in the other. They must never be collapsed:

| | Question it answers | Frontera today |
|---|---|---|
| **Authorization security** | Is this actor legitimately allowed to perform this *declared* action? | Mature. Single decision producer, narrowing-only composition, fail-closed bounded-grant exercise, structural boundary tests that fail CI. |
| **Containment security** | What can this actor technically reach, execute, mutate, read, exfiltrate or destroy if it behaves maliciously? | Essentially absent. No process isolation, no egress control, no capability dropping, no aggregate bounding, no durable kill switch. |

Every invariant in §4 is an authorization-security or structural-hygiene invariant. Every entry in §7 is a containment-security invariant, and every one of them is unimplemented or partial.

## 3. Scope Vocabulary

Every invariant carries exactly one scope.

| Scope | Meaning |
|---|---|
| **SYSTEM-WIDE** | Proven to hold across every relevant production path in this repository. Where a named exception exists, the invariant is not system-wide and must be scoped down instead. |
| **LAYER-LOCAL** | Holds only within named architectural layers (`ADR-AUTHORITY-CONTROL-LAYERING.md` A–G). Says nothing about other layers. |
| **PATH-LOCAL** | Holds only for one end-to-end execution/effect path. Says nothing about the other effect paths in §5. |
| **COMPONENT-LOCAL** | Holds only for a specific named service, store, module or application. |
| **DEPLOYMENT-CONTRACT** | Depends on infrastructure or operator configuration outside this repository's control. The repository can state the requirement; it cannot enforce it. |
| **ASPIRATIONAL-UNIMPLEMENTED** | A desired property that is not currently enforced by anything. Recorded so it cannot be mistaken for a guarantee. |

Enforcement strength is stated separately, and more than one value may apply:

| Enforcement | Meaning |
|---|---|
| **STRUCTURAL** | A build- or test-time check fails if the property is violated, independent of runtime input. |
| **RUNTIME** | Production code checks the condition at runtime and fails closed. |
| **TYPE-LEVEL** | The TypeScript type system makes the violation unexpressible. |
| **TEST-ENFORCED** | A test asserts the behaviour; `npm test` runs on every PR and push to `main` (`.github/workflows/ci.yml`). |
| **DOCUMENTED** | Stated in an ADR, doc comment or design document, with no structural or runtime mechanism proving it. |
| **DEPLOYMENT-DEPENDENT** | Holds only if the operator configures the deployment as documented. |
| **NOT IMPLEMENTED** | No mechanism exists. |

`DOCUMENTED` alone is never a guarantee. It records intent.

## 5. Execution Path Guarantees

Frontera has **four** distinct effect models. Conflating them is the single largest overclaim risk in this repository.

> **Complete inventory.** These four models are the *shapes*. The exhaustive, per-path enumeration — sixty-seven production-capable effect paths (re-enumerated from source by CORE-06; CTRL-02 added EP-063 … EP-066; CTRL-03 added EP-067), each with a stable `EP-` id and exactly one classification — is `docs/security/NO_BYPASS_AUTHORITY_CONTROLLED_EXECUTION.md` §5. Rule 4 of §9 below is satisfied by adding a path there as well as here.

### 5.1 Evaluation — `AocKernel.evaluate()` / `POST /api/governance/evaluate`

- **Guarantees:** a decision, with reason codes, a trace, and a durably committed Governance Record. Recognition precedes any allow. Narrowing-only composition. No mutation of the request.
- **Does not guarantee, and does not attempt:** anything about execution. It invokes nothing.
- **Invariants:** SEC-INV-001 … SEC-INV-008.

### 5.2 Decision-time enforcement — `AocKernel.enforce()`

- **Guarantees:** the declared action passed authorization — recognition, authority, policy, context and blocking obligations — *before* the supplied executor was invoked, and the executor is not invoked at all on any non-allow outcome.
- **Does not guarantee:** that the executor's actual external effect corresponds to the declared `ActionDescriptor`. The executor is an opaque closure and is never inspected.
- **The correct formulation:**

  > `AocKernel.enforce()` = **decision-time** authorization of a **declared action**.
  > Bounded-grant exercise = **effect-time** authorization of a **validated execution action**.

- This is an accepted architectural boundary, not a defect. No accepted ADR gives grants a role in the executor gate, and grants deliberately do not gate `enforce()`.
- **Invariants:** SEC-INV-009 (guarantee), SEC-INV-010 (limit).

### 5.3 Bounded-grant exercise — `GrantExecutionService` / `AuthorityControlledExecutionService`

- **Guarantees:** the strongest execution-time property in the repository. The authoritative store is re-read on every attempt; twelve checks run fail-closed; every failing axis is reported; the adapter receives only values an assessment proved, across a boundary with no free-form payload channel and a build-enforced 17-field whitelist.
- **Does not guarantee:** anything about the other three paths. It is **opt-in**. Since P5 it has exactly one HTTP entry, `POST /api/governed-actions`, which enters at the **top** — customer admission, then the Governed Action Orchestrator — and exposes no grant, exercise, routing or emergency-control surface (SEC-INV-055 … SEC-INV-061).
- **Invariants:** SEC-INV-011 … SEC-INV-018, SEC-INV-027, and — when a deployment composes them — SEC-INV-039 … SEC-INV-054, for the customer route SEC-INV-055 … SEC-INV-061, for P7 exercise controls SEC-INV-070 … SEC-INV-079, for the P8 canonical authority event stream SEC-INV-080 … SEC-INV-088, for P9 canonical monetary semantics SEC-INV-089 … SEC-INV-093, for P10 authority-sourced payment ceilings and durable spending limits SEC-INV-094 … SEC-INV-101, for P11 durable monetary outcomes and provider certainty SEC-INV-102 … SEC-INV-110, and — when composed — for P12 execution reconciliation and resolution authority SEC-INV-111 … SEC-INV-122.
- **Since P12:** when `executionReconciliation` is composed, every new governed execution is durably bound to one trusted resolution authority before its claim; an execution P11 left uncertain can later be resolved — only by that authority, only through the trusted in-process reconciliation service, never by replay, a caller or a retry — into a new immutable resolution that never rewrites P11; a proven non-completion returns its P7 capacity through a second immutable ledger row bound to the resolution digest, committed only after the resolution (SEC-INV-111 … SEC-INV-122).
- **Since P11:** every governed execution's exact prepared context is durable before its claim and provider crossing, and its initial provider observation — `confirmed-completed`, `confirmed-not-completed` or `unconfirmed`, with attribution and an opaque `providerRef` — is durable and immutable once obtained; replay answers from it without a provider call, and an unobserved or unverifiable execution stays unresolved and is never retried (SEC-INV-102 … SEC-INV-110).
- **Since P10:** a host-classified financial action is issued a grant only under durable monetary authority on the lineage that authorized it — the grant's amount ceiling is that authority's `max_amount`, never the requested amount — and its exercise consumes the authority's durable `spending_limit`s through P7's one atomic reservation, with the financial authority revalidated at the commit boundary and before and after the reservation (SEC-INV-094 … SEC-INV-101).
- **Since P8:** when governed actions are composed, the lifecycle on this path is also recorded as a canonical, ordered, hash-chained, tenant-confined event stream — after each fact, never before it, read by nothing that decides and **never awaited by authority control flow** (SEC-INV-080 … SEC-INV-088). Evidence only: it adds no authorization guarantee and cannot weaken any check above. Projection still shares the process and event loop and may add process latency; see SEC-INV-088.
- **Since P7:** when `exerciseControls` is composed, repeated use is bounded too — aggregate count, aggregate amount and rolling velocity limits admitted atomically through a durable reservation before the adapter, conservative settlement, and exact-equality revalidation of the grant's authority binding before and after the reservation, with the grant itself re-read and re-assessed after the reservation (SEC-INV-070 … SEC-INV-079). Path-local: per-action containment elsewhere is unchanged, and no other path gains aggregate control.
- **Since Prompt 4:** the adapter this path invokes may be the composite `createExecutionAdapterRegistry(...)`, which routes server-side to exactly one trusted child (SEC-INV-039 … SEC-INV-042); and, when composed, a durable operational interlock is consulted at four points and fails closed when unreadable (SEC-INV-043 … SEC-INV-052). Neither changes what authorizes an action: routing chooses where, and the interlock can only withhold.

### 5.3a Generic HTTP adapter outbound request (P6) — EP-050

- **Guarantees:** when the bounded-grant path routes to a Generic HTTP child, at most one HTTPS request per `execute()`, to the one operator-pinned origin, over a fresh connection to an address resolved for that execution and proven publicly routable, TLS verified with `rejectUnauthorized: true` hardcoded (immune to `NODE_TLS_REJECT_UNAUTHORIZED=0`), no redirect, no retry, no reuse; completion declared only for 200, 201 and 204; outbound values are operator literals or approved `ValidatedExecutionAction` fields (since CORE-08 including its exercise-contained typed parameters, into value positions only — SEC-INV-181, SEC-INV-182); post-send uncertainty is `execution_unconfirmed` (SEC-INV-062 … SEC-INV-069).
- **Does not guarantee:** system-wide egress control (SEC-INV-U03), provider-side exactly-once, reconciliation of `execution_unconfirmed`, protection from a provider that forwards the request, or anything about Pinata, Stripe, Sovereign Access, Content Protection or `enforce()`. It governs no other path retroactively.
- **Invariants:** SEC-INV-062 … SEC-INV-069, on top of every invariant of §5.3.

### 5.4 Sovereign Access provider execution

- **Guarantees:** its own authority model — an authoritative `EnterpriseAccessGrant` store read plus an active-status check — before minting a provider credential or enforcing a provider-side revocation.
- **Does not guarantee:** bounded-grant exercise semantics. It does not call the Kernel and does not read a `BoundedGrant`.
- **Explicit statement required by this document:**

  > The invariant "no adapter call without a usable bounded-grant exercise" (SEC-INV-011) **does not currently apply to Sovereign Access provider execution.**

- **Prompt 3 decided: record it as an explicit exception rather than converge it** (`NO_BYPASS_AUTHORITY_CONTROLLED_EXECUTION.md` §9.4). A **second** provider authority model reaching the same resource was also found there and is excepted on the same terms: Content Protection (`src/enterprise/content-protection`), gated only by a caller-asserted tenant scope (NB-003).
- **Invariants:** SEC-INV-019.

### 8.2 We Cannot Claim Yet

1. **Rogue-agent containment.** Frontera governs declared actions; it contains nothing (SEC-TRUST-004, SEC-TRUST-005).
2. **Sandboxing or agent isolation.** No sandbox, no isolation primitive, no agent execution runtime (SEC-TRUST-005).
3. **System-wide adapter gating.** SEC-INV-011 is PATH-LOCAL. It does not hold for `enforce()`, for Sovereign Access, or for Content Protection (SEC-INV-010, SEC-INV-019, NB-003). Eight of sixty-seven effect paths are bounded-grant controlled. CTRL-03 raised only the denominator, by one: the web control plane (EP-067) is a separate operator-run process whose one outbound call reaches the Host's operator API with the signed-in operator's credential; everything it can change is an existing operator-plane path, authorized again by the Host. CTRL-02 raised only the denominator, by four: the operator plane's provisioning, agent-credential issuance and revocation, and Governance Profile lifecycle writes (EP-063 … EP-066) are deployment-gated authority and identity writes, none bounded-grant controlled and none a way to reach a provider. CORE-06 raised only the denominator, by five: re-enumerating from source found obligation discharge recording (EP-058), the durable approval commands (EP-059), the reference signer and witness processes (EP-060, EP-061) and the CTRL-01 administration HTTP entry (EP-062) inventoried nowhere — none bounded-grant controlled. CORE-07 and CORE-02 each raised only the denominator, by one: the authority-state witness request (EP-057) and the external signing request (EP-056) are deployment-gated calls outside the bounded-grant gate. P12 raised only the denominator, by two: its status query (EP-054) and P7 resolution row (EP-055) are deployment-gated trusted in-process paths, not bounded-grant ones. P7 raised both numbers by three, because its three new paths — the exercise-control reserve, settle and release writes (EP-051 … EP-053) — are local authority-state writes reachable only inside the bounded-grant gate, not provider effects and not any other path becoming governed. P6 raised both numbers by one because its one new path, EP-050, sits below the bounded-grant path, not because any other path became governed. Prompt 4 raised the denominator rather than the numerator; P5 raised both by one, because its one new path — the customer HTTP entry, EP-049 — is itself the bounded-grant path, not because any other path became governed (NO_BYPASS §5.11).
4. **Cryptographically authenticated authority artifacts — *partially*, as of Prompt 5.** Bounded grants and grant revocations in the **durable** store are signed and verified (Ed25519, public-key verification, no unsigned mode). Everything else still relies on unkeyed digests, and Agent Passport on HMAC. So the general form of this gap remains open (SEC-TRUST-002, SEC-INV-U01), narrowed to one path.
5. **KMS/HSM-protected signing.** Still absent — no KMS or HSM integration ships. CORE-02 ships an external-signer boundary and a *reference* custody service (not an HSM): under external custody the authority private key is not in the Frontera process (SEC-INV-147), but a compromised Host can still request signatures while it holds the service credential (AA-010). The symmetric HMAC secrets, and the authority key under software custody, remain process-resident (SEC-INV-U02, AA-001).
6. **One durable kill switch across every authority-bearing path.** A durable interlock now covers the bounded-grant / Governed Action path and fails closed when unreadable (SEC-INV-043 … SEC-INV-052, `AOC_EMERGENCY_CONTROL.md`), and it is opt-in. It does **not** cover `AocKernel.enforce()`'s Action Enforcement path — which keeps its separate, process-local, non-durable `emergencyDeny` — nor Sovereign Access, nor Content Protection. "Frontera has a global kill switch" is false; "the bounded-grant path has a durable, fail-closed operational stop when configured" is true (SEC-INV-U05).
7. **Behavioral abuse detection, and aggregate control beyond one path.** No behavioural or anomaly analysis anywhere, and the authorization layers are structurally banned from containing any. P7's host-declared count, amount and velocity limits hold **only** on the P7-enabled bounded-grant exercise path (SEC-INV-070 … SEC-INV-079); "Frontera bounds aggregate behaviour" is false, "the bounded-grant path bounds aggregate use of a grant when exercise controls are composed" is true (SEC-INV-U06).
8. **A hardened SaaS surface.** One blocker (APW-001, unauthenticated credential disclosure at checkout) is remediated and regression-tested, but APW-002, APW-003, APW-006 and APW-007 remain open in `AGENT_PASSPORT_WEB_THREAT_MODEL.md`.
9. **Complete repository threat-model coverage.** `src/enterprise` and `apps/agent-passport-web` are now modelled, but `packages/*` libraries remain outside every threat model (`THREAT_MODEL_V1.md` §9), and no independent penetration test has been performed against any surface.
10. **Durable authorization state by default.** A durable bounded-grant store now exists and is production-capable, but it is selected only when `persistence.provider === 'sqlite'`; recognition, approval, capability-token and policy-pack state remain in-process under **every** configuration (SEC-TRUST-003, GS-003). "All Frontera authority is now durable" is false.
11. **Anti-rollback on the authority store — without a freshness witness, or against a witness restored with it.** With an external authority-state witness (always, on the secure Host), a restored earlier authentic state of the grant, discharge or approval store is refused across restarts (SEC-INV-164 … SEC-INV-175, CORE-07). Without one — a lenient embedding — restoring a pre-revocation snapshot restores the revoked grant once the process restarts, and CORE-01 detects it only within a running process (SEC-INV-124). With one, restoring the witness's state together with the authority store to the same earlier moment is undetectable, and a rollback before a store's first trusted enrollment is not detected. "Frontera makes arbitrary infrastructure snapshots safe" is false (`AUTHORITATIVE_GRANT_STORE.md` §17).
12. **Tamper-proof authority storage.** Store digests are unkeyed; a writer who can re-seal defeats every integrity check (SEC-TRUST-002). The durable bounded-grant store now also requires a trusted signature, which blocks a **database-only** re-sealer there (SEC-INV-123, GS-001), and a signed revocation-state commitment that blocks database-only revocation removal (SEC-INV-124) — but a holder of the process-resident signing key or of the trusted-key configuration still forges freely (AA-001, AA-002), snapshot rollback is refused only where an external freshness witness is composed (GS-002, CORE-07), and every other store remains re-sealable.
11. **Third-party-verifiable Agent Passports.** They are HMAC-signed; the registered "public key" is symmetric-scheme metadata and cannot verify them.
12. **Repository-wide capability restriction.** Proven for five modules; absent for `packages/`, `apps/` and most of `src/enterprise` (SEC-INV-U08).
13. **System-wide network egress control.** The Generic HTTP adapter pins its own destination; nothing prevents other process code — or the Pinata and Stripe paths — from reaching the network (SEC-INV-U03, SEC-TRUST-004). "Frontera blocks unauthorized egress" is false.
14. **Exactly-once external execution.** P7 adds a reservation keyed to the execution identity, so one identity cannot invoke an adapter twice on the P7-enabled path (SEC-INV-077) — still not exactly-once. P6 gives a durable write-ahead claim before any adapter invocation, at most one outbound request per `execute()`, no automatic retry, an operator-mappable provider idempotency value, and honest `execution_unconfirmed` reporting. It gives no provider-side idempotency guarantee, no reconciliation and no automatic recovery (SEC-INV-068, SEC-INV-069). P12 adds explicit, trusted reconciliation — a host-composed resolution authority may later establish whether an uncertain effect completed — but no automatic recovery, no retry and no exactly-once: an execution no trusted authority can answer stays unresolved (SEC-INV-111 … SEC-INV-122).
15. **Distributed or cross-host quota.** P7 serializes admission within one SQLite file on one host. Separate ledgers on separate hosts do not share a quota, there is no consensus, and there is no automatic abandoned-reservation recovery (SEC-INV-071, SEC-INV-072). Since P12 a reservation's capacity returns only through an explicit, trusted reconciliation that durably proved non-completion — never by time or restart (SEC-INV-117, SEC-INV-120).
16. **A tamper-proof, authenticated, complete or system-wide event record.** The P8 stream is tamper-*evident* with unkeyed digests — not signed, not WORM, not non-repudiable, not replicated — and it covers the governed-action / bounded-grant lifecycle only; `evaluate()`, `enforce()`, Sovereign Access, Content Protection and application code emit nothing into it. Its order is per stream, not global, and a projection that failed — or that was still queued when the process stopped — is not retried or reconciled, so it is neither exactly-once nor complete: verification proves the integrity and order of what is present, and an absent event is never evidence that its fact did not occur (SEC-INV-084, SEC-INV-085, SEC-INV-088).
17. **Universal action neutrality.** CORE-08 qualifies three reference domains (treasury, DevOps, customer data). "Every machine action is supported" is false; a new domain is expressed as profile, context-source, policy, authority and adapter data and qualified on its own (SEC-INV-184).
18. **Physical-actuation safety.** No fail-safe semantics, real-time bounds or human-in-the-loop guarantee for industrial systems, robots, vehicles or medical devices is claimed or tested (Master Plan §4.2, OQ-15).
19. **Rail neutrality.** CORE-08's treasury domain executes through Generic HTTP; XRPL versus Lightning neutrality is PAY-07 / CORE PROVEN (Master Plan §11.2), not demonstrated.

## 9. Change Control

1. **Promotion requires proof.** An invariant's scope may only be widened — PATH-LOCAL to LAYER-LOCAL, LAYER-LOCAL to SYSTEM-WIDE — when code or a test actually proves the wider scope. Changing the prose is not promotion. A scope change with no corresponding test change should be rejected in review.
2. **Local invariants must never be represented as system-wide claims.** Any external artifact — architecture document, README, datasheet, sales material, model-facing summary — that repeats an invariant from §4 must carry its scope. SEC-INV-011 in particular must always name the bounded-grant path.
3. **Weakening requires review.** Removing an enforced invariant, or reducing its enforcement strength, requires an explicit architecture decision and a corresponding update to the tests named in its Evidence column. A test deleted without an entry here being updated is a regression, not a cleanup.
4. **New effect paths must declare themselves.** Any new path capable of producing an external effect must be added to §5 with its own guarantees and non-guarantees, **and to `NO_BYPASS_AUTHORITY_CONTROLLED_EXECUTION.md` §5 with its own `EP-` id and classification**, before it ships. A path absent from either is covered by no invariant here and by no claim there. `src/enterprise/__tests__/no-bypass-effect-paths.test.ts` fails the build when a new provider SDK site, execution-adapter invocation, route file or Server Action appears without that update.
5. **Boundary statements are not optional.** §6 travels with §4. A security claim quoting §8.1 without the relevant §6 assumption is incomplete.
6. **Unimplemented stays unimplemented until owned.** An entry in §7 moves into §4 only when its owner prompt lands the mechanism and the evidence.
