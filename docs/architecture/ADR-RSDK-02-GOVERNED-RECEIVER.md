# ADR — RSDK-02B: governed sovereign receiver (internal)

**Status:** implemented, internal and unpublished. **Scope:** one synthetic protected operation, one local receiver, one
consumption domain. Not production-ready.

## Decision

A receiving application acts on a portable sovereign asset only when all three hold:

1. **Authority.** A Frontera G-02 execution capability, signed under a pinned issuer key, authorizes exactly the request
   received: audience, organization, trust domain, action, validity window, and the
   `frontera.http-request-binding.v1` digest the receiver rebuilds from the bytes it received.
2. **Authenticity.** RSDK-01 verifies the receiver's stored bundle for exactly the capability's resource.
3. **Eligibility.** The receiver's own policy explicitly returns `eligible` for that verified asset and that action.

Only then is the capability claimed in the existing durable consumption ledger and the protected operation attempted,
once. `verified` (RSDK-01) is authenticity, never authority. The capability alone is authority, and the receiver's
policy decides whether to use it.

It is implemented as `src/enterprise/governed-receiver/`, an executor-side module composed from the existing G-02
executor:

| Step | Component | New or reused |
|---|---|---|
| admission, credential, presentation, binding rebuild, G-02A verification, eligibility | `createReferenceExecutorVerificationPipeline` | reused; its one static check, the resource allow-list, is replaced by the sovereign identifier rule through a new optional `resourcePermitted` predicate (default behaviour unchanged) |
| asset load, size cap, RSDK-01, policy | `asset-gate.ts` | new |
| durable claim, expiry re-check, synthetic effect, forward-only outcome, receipt | `createReferenceExecutorExecutionFlow` | reused unchanged, handed the verdict already computed (a pinned pipeline), so nothing is verified twice on a moved clock |
| receipts | G-02C1C issuer, ledger and signer | reused unchanged |

There is no new Host endpoint, no new capability or receipt schema, and no change to the Host, Kernel, issuance,
custody, gate or evidence recorder.

## The precomputed verdict

The existing flow verifies through an injected pipeline. The receiver hands it a pipeline that returns, once and only
for the identical request object, the verdict computed before the asset gate ran. This is safe because the flow reads
the request only through that pipeline: the claim, the effect and the receipt come from the verified capability and its
binding digest, never from the request again. The pinned pipeline and the flow are built per request and discarded with
it. Tests pin this:

- interleaved requests each act on their own verdict;
- a request delivered twice concurrently is claimed and performed once;
- mutating the received request while the gate is suspended changes nothing that is executed;
- a capability that expires during the gate is refused at the claim.

## The resource predicate

`createReferenceExecutorVerificationPipeline` takes an optional `resourcePermitted` predicate. Only the governed
receiver passes one, the module constant `isSovereignAssetIdentifier`; the reference gateway and launcher keep the
static allow-list. The predicate is read once and replaces only the allow-list check. Binding reconstruction, G-02A
verification (signature, audience, organization, trust domain, window, action, resource, binding) and eligibility
always run after it. It can refuse, never admit past them. A throw refuses (`EXECUTOR_FAILURE`), and any answer other
than `true` refuses.

## Dependency boundaries

- The shipped root runtime must keep `@aoc/protocol` type-only (`validate-publishability` scans every shipped JS file).
  The receiver therefore never imports RSDK-01 or `@aoc/protocol`, not even for types. RSDK-01 is **injected** as
  `verifyAsset`, a trusted deployment dependency composed at startup with the deployment's own key resolver and
  consumer support. A request can select neither the verifier, the policy, the store nor the effect.
- Workspace packages never import root `src`. The composition with the real RSDK-01 happens only in non-shipped tests
  (`tests/rsdk02-governed-receiver.e2e.test.mjs`).
- `ALLOWED_PROTOCOL_SUBPATHS` is unchanged. The integration fixture is generated by
  `packages/sovereign-receiver-verification/scripts/generate-governed-receiver-fixture.mjs`, inside the package-scoped
  allowance, with throwaway keys whose private halves are never written.

## The resource convention

For this integration profile, `capability.resource` **is** the sovereign asset identifier
(`aoc:sovereign-asset:<uuid>`). The receiver checks its shape before loading anything, and passes it to RSDK-01 as
`expectedSovereignAssetId`. It is never taken from the request body or path: those are bound by the capability's
binding digest, and a request whose path names another asset fails that binding. Grants for receiver actions must use
this resource convention.

## Order, deadlines and failure model

```
verify capability → [synthetic action?] → [already consumed? → already-consumed] → asset gate (load → size → RSDK-01 → policy) → claim → expiry → effect → outcome → receipt
```

- **Nothing is claimed before the capability and the asset have both passed.** Every asset-gate refusal leaves the
  capability unclaimed. Store and verifier outages and timeouts answer 503; every other refusal answers 403.
- **The asset gate is the only awaited part.** Its three stages share one absolute budget, set once and never reset: the
  configured deadline (default 5 s, at most 30 s), shortened to the capability's remaining validity. The budget is
  re-read on the receiver's clock whenever a stage's result is accepted, and once more before an eligible decision is
  (RSDK-02D). A stage that blocks the event loop past the deadline, so its timer has not yet fired, is still a timeout.
  This is a deadline, not cancellation: a store, verifier or policy that is still running is not stopped, and its late
  answer is discarded.
- **A consumed capability keeps its consumed answer (RSDK-02D).** After G-02 verification, and only with the verified
  capability and execution ids, the receiver reads the ledger (its existing read-only `read` and `readExecution`). An
  already-consumed capability, or one whose execution was consumed, skips the asset gate and is answered
  `already-consumed` (202) directly from the durable state found, with the receipt that state supports, exactly as the
  existing flow would. No second claim is attempted: the ledger's claim checks expiry before consumption, so a claim
  would turn a consumed capability that has since expired into a refusal. An earlier uncertain attempt is therefore never turned into a definitive
  refusal by current asset eligibility. Because the gate awaits, the ledger is read again before any gate refusal is
  answered, refusal or not: a concurrent delivery that claimed the capability meanwhile also yields `already-consumed`. An unreadable
  ledger, at either read, answers `claim-unavailable` (503), with nothing performed.
  The atomic claim stays the race-safe enforcement point for unconsumed capabilities.
- **Bundles are capped at 1 MiB of UTF-8** (a deployment may set less) before RSDK-01 parses anything.
- **The policy answer must be exactly** `{ decision: 'eligible' }` or `{ decision: 'ineligible', reason }` as own data.
  Anything else, including a throw or a hang, refuses.
- **The claim re-checks expiry, and the flow re-checks it again before the effect.** From the claim to the recorded
  outcome the existing flow awaits nothing: the synthetic effect is synchronous.

## Crash behaviour and outcomes

- A claim is committed (`IMMEDIATE`, `synchronous=FULL`) before the effect. After a crash past the claim the row stays
  `claimed`, and the capability and its execution id are never claimable again.
- The effect is never retried. A failed effect is recorded `failed`; an uncertain one is `outcome-unknown`, or stays
  `claimed` if nothing could be recorded. None is ever reported as completed.
- If the existing flow throws, the receiver reads the ledger. A committed claim is answered `attempted-outcome-unknown`
  (502), never as a refusal.

## Receipts

Receipts are the existing `frontera.executor-receipt.v1`, which this profile does not change. A receipt proves that
the pinned executor key signed what the executor says it observed. It does not prove an external effect happened, or
happened exactly once (`externalConfirmation: not-established`). `completed-observed` requires the synthetic
deployment record observation, so this profile supports **only the synthetic operation**; receipting any other
protected operation would need a receipt contract change.

## Limitations (not claimed)

- **Freshness and revocation are not evaluated.** RSDK-01 cannot detect a bundle that omits a newer manifest version (a
  later withdrawal, for example), and no asset revocation source exists. A capability's own revocation exposure is
  bounded by its window (at most 60 s, offline-permitted only).
- **Single use is per consumption ledger.** Two receivers with separate ledger files would each accept a capability
  once. This demonstration uses one local receiver and one ledger. Sharing a ledger across processes is supported only
  on one local filesystem.
- **No exactly-once external effect.** The ledger makes the authorization usable at most once; it does not make a side
  effect happen exactly once.
- **The demonstration policy is not a production authorization policy.** It assumes, for the synthetic test only, that
  the stored bundle is the asset's current representation.
- **No production front end.** The demonstration's loopback HTTP server is test code; the reference gateway's hardened
  handling is synchronous and is not reused here. TLS termination in front of a receiver is a deployment prerequisite.
- The resource allow-list in the reference configuration is not consulted in receiver mode: the sovereign identifier
  rule and the per-asset policy replace it.

## Deployment prerequisites (beyond this demonstration)

- Frontera issuer keys pinned out of band.
- A capability-gated Generic HTTP adapter on the Host, whose audience is registered with
  `frontera.http-request-binding.v1` and pinned to exactly this executor.
- An operator-initialized consumption ledger (and receipt ledger) for the audience.
- The deployment's trusted sovereign key resolver and consumer support.
- A trusted asset store holding the bundles (and content bytes) for the assets the receiver will act on.
